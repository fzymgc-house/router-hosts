  `delete`, and no Service status subresource.
- **Events** (`""`): create, patch, cluster-wide — the controller reports

**4. New `### Sync Kubernetes Services` section** under `## Usage`, placed after
"Sync Gateway API Routes". Mirror that section's structure: one sentence of
intent, a YAML example, then behavioral notes. Cover:

- The two independent gates (D-03): `serviceController.enabled: true` on the
  chart AND `router-hosts.fzymgc.house/enabled: "true"` on each Service. Neither
  substitutes for the other, and a Service without the annotation is never
  touched.
- An annotation reference table with all four keys, whether each is required, and
  what it does: `router-hosts.fzymgc.house/enabled` (required, `"true"` to opt
  in); `router-hosts.fzymgc.house/hostname` (required, exactly one hostname — a
  Service has no hostname in its spec, which is why registration is explicit);
  `router-hosts.fzymgc.house/aliases` (optional, comma-separated, mapped to the
  entry's native aliases, invalid entries dropped with a warning);
  `router-hosts.fzymgc.house/ip-address` (required for NodePort, optional
  override for LoadBalancer).
- A YAML example of a LoadBalancer Service carrying `enabled`, `hostname`, and
  `aliases`.
- **Supported types**: only `LoadBalancer` and `NodePort`. `ClusterIP`,
  `ExternalName`, and headless Services are unsupported; annotating one produces
  an `InvalidServiceType` warning Event and no entry.
- **IP resolution**: for LoadBalancer, the first `status.loadBalancer.ingress[]`
  entry with a non-empty `ip`, in declaration order; entries carrying only a
  hostname (AWS ELB style) are skipped, because a CNAME target is not a host
  entry IP. While no IP is available the Service is retried and no IP-less entry
  is ever created. For NodePort the IP comes only from the `ip-address`
  annotation, because a NodePort is exposed on every node and which address to
  publish is topology-dependent. The `ip-address` annotation overrides
  LoadBalancer status when both are present.
- **No default fallback**: state explicitly that `routerHosts.defaultIngressIP`
  is NOT used for Service-derived entries, unlike IngressRoute- and
  Gateway-derived ones, and give the reason — a Service's IP is knowable from the
  object itself, so a default would be a guess, and sharing that IP across
  controllers is what makes cross-controller hostname collisions routine (D-11).
- **Events**: the four reasons a Service owner may see — `InvalidServiceType`,
  `MissingHostname`, `MissingIPAddress` (all Warning) and `PendingLoadBalancer`
  (Normal) — visible via `kubectl describe service`. Note that success is logged
  by the operator rather than evented, to keep the event stream usable.
- **Cleanup**: the operator adds a `router-hosts.fzymgc.house/service-cleanup`
  finalizer and removes the DNS entry when the Service is deleted, when it is
  opted out, when its type changes to an unsupported one, or when its hostname
  annotation changes.
- **Cache footprint** (D-04): the operator's shared informer caches every Service
  in the cluster once this is enabled, not only the annotated ones, because a
  cache selector can filter on labels but not on annotations. State the tradeoff
  plainly — it is fine at homelab and small-cluster scale, and a label-based
  opt-in is the change to make if the operator ever runs against a cluster with
  thousands of Services.
- **Not supported in this release**: multi-IP / dual-stack (AAAA) entries,
  hostname-typed LoadBalancer ingress, deletion grace periods, and a
  user-supplied tags annotation.

<threat_model>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Helm values → operator process arguments | `serviceController.enabled` decides whether the operator watches and writes DNS for Services at all |
| Helm chart → cluster RBAC | The rendered ClusterRole is the authorization boundary for every Service read and write |
| README → cluster operator | Documentation is the only description of an opt-in contract that lives entirely in annotations |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-08-08 | Elevation of Privilege | chart upgrade silently enabling the Service watch | medium | mitigate | `serviceController.enabled` defaults to `false` and the arg is emitted only under it, so upgrading the chart never starts a Service watch or writes a DNS entry (D-03, the T-07-17 class). Task 2 assertion 1 fails the build if the default render ever contains the flag. |
| T-08-05 | Elevation of Privilege | over-granted `services` RBAC | medium | mitigate | Task 2 assertion 3 compares the rendered `services` verbs line against the exact five-verb string, so adding `delete`, `create`, or a wildcard is a hard test failure rather than something a reviewer must notice. Assertion 5 rejects the Service status subresource. Both are proven to actually fail by the negative control in the acceptance criteria. |
| T-08-04 | Repudiation | events RBAC silently regressing | high | mitigate | Task 2 assertion 4 counts the cluster-scoped `events` rule and checks `create` and `patch` independently on the rendered verbs line. A silently removed rule fails the build; without this, a regression would only surface as events that stop appearing in a live cluster, which nobody notices. The second negative control proves the assertion fires. |
| T-08-20 | Repudiation | assertion staleness in `test:chart` | medium | mitigate | The Phase 7 regression is the direct motivation: an assertion built on `grep -q` can pass by matching nothing. Every new assertion captures rendered output and compares or counts it, printing the observed value on failure, and the two negative controls in the acceptance criteria empirically prove each new gate fires when the chart is wrong. |
| T-08-10 | Denial of Service | cluster-wide Service informer cache | low | accept | Accepted under D-04 — a cache selector cannot filter on an annotation, and switching the opt-in contract to a label would be a breaking change (Deferred Idea). Task 3 documents the footprint and names the alternative so an operator running at a scale where it matters can make an informed decision rather than discovering it as an outage. |
| T-08-21 | Tampering | operator enabling the wrong values key | low | mitigate | The deliberate `serviceController` versus `gateway.enabled` asymmetry is a real footgun in both directions: an operator may set the conventional key and get nothing, and an agent may "fix" the key back to the conventional one and break every existing values file. Documented in `values.yaml` and in the README, and pinned by task 1's assertion that the conventional key is absent from `values.yaml`. |
