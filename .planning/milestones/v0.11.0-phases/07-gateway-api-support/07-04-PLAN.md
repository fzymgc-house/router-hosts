# Phase 7 Plan 04 — Route Lifecycle: Update, Delete, and Fail-Closed Safety

<objective>
Make the route lifecycle total: edits converge, deletions clean up, partial
failures never orphan an entry, and a corrupt tracking annotation fails closed.

Purpose: GW-01's third success criterion is "deleting or editing a route
updates/removes the corresponding DNS entries". Everything before this plan only
creates. This is also where the phase's two sharpest data-loss risks live —
deleting an entry another controller owns, and proceeding on a half-read
annotation.
Output: a complete `syncRoute` diff and a complete `reconcileDelete`.
</objective>

  <action>
Complete `(r *GatewayRouteReconciler) syncRoute` in
`internal/operator/gateway_controller.go`, mirroring
`ingressroute_controller.go`'s `reconcileUpsert` control flow (lines 118-191).

Read `existingIDs` via `getHostIDsAnnotation(log, obj)`. On error, return
`ctrl.Result{RequeueAfter: requeueDelayShort}` and the error itself — this is the
corrupt-annotation fail-closed path from D-14; do not swallow it, do not treat the
map as empty, and do not proceed to any `HostClient` call, because proceeding on a
partial view would delete entries the annotation no longer describes.

Build `newIDs := make(map[string]string)` and loop over the filtered hostnames:

- Already in `existingIDs`: call `r.HostClient.UpdateHost(ctx, id, ip, hostname,
  comment, nil, tags, "")` unconditionally. Do NOT port `syncHost`'s
  GetHost-before-Update idempotency guard from the IngressRoute controller — D-13
  locks the unconditional call here because it is what propagates a changed
  Gateway IP without the controller keeping extra state. Leave a code comment on
  `syncRoute` recording that this divergence is deliberate and pointing at D-13,
  so a future reader does not "align" it with `syncHost` without re-deriving the
  tradeoff. On failure: log at error level, keep `newIDs[hostname] = id` so the
  stale-cleanup pass below does not mistake it for a removed host, set the error
  flag, and continue to the next hostname.
- Not yet tracked: call `r.HostClient.AddHost(ctx, ip, hostname, comment, nil, tags)`
  and record the returned ID. On failure: log at error level, record nothing for
  that hostname, set the error flag, and continue. There is no adoption or
  AlreadyExists retry path in this controller — D-13's design does not use
  `GetHost` or `FindHost`.

Then the stale-cleanup pass: for every `hostname, id` in `existingIDs` with no
entry in `newIDs`, call `r.HostClient.DeleteHost(ctx, id)`. On failure, retain
`newIDs[hostname] = id` so the ID is not orphaned, and set the error flag. Every
deletion target comes from this object's own annotation — never from a hostname
lookup, an IP lookup, or a cross-object query.

Persist only when the map actually changed: guard `setHostIDsAnnotation(obj, newIDs)`
plus `r.Update(ctx, obj)` with `!maps.Equal(existingIDs, newIDs)` (D-13). A no-op
`Update` bumps the resourceVersion and re-triggers the watch for nothing.

Return `ctrl.Result{RequeueAfter: requeueDelayLong}` with a nil error when the
error flag is set, otherwise the zero `ctrl.Result` with a nil error. Wrap the
annotation-set and object-update failures with `oops.Wrapf`. Reuse the existing
`requeueDelayShort` and `requeueDelayLong` constants.

<threat_model>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Kubernetes API server → operator | The `host-ids` annotation is on a user-editable object; a cluster user can hand-edit or corrupt it |
| operator → router-hosts gRPC server | `DeleteHost` is destructive and irreversible from the operator's side |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-07-02 | Tampering | `syncRoute` stale-cleanup and `reconcileDelete` | high | mitigate | Ownership is per-object: every `DeleteHost` argument is read from the reconciled object's own `host-ids` annotation, never from a hostname or IP lookup. A hostname shared with another route, a HostMapping, or an IngressRoute therefore cannot make one controller delete another's entry. `TestSyncRoute_NeverDeletesUntrackedID` and `TestSyncRoute_DuplicateHostnameAcrossRoutesDoesNotCrossDelete` are the standing proofs. |
| T-07-04 | Tampering | `getHostIDsAnnotation` corrupt-JSON path | high | mitigate | A corrupt annotation returns an error and requeues in both `syncRoute` and `reconcileDelete`, never proceeding on a partial view. Proceeding would treat every tracked-but-unreadable hostname as removed and delete its live entry — silent data loss. Two dedicated tests assert zero `HostClient` calls on that path. |
| T-07-13 | Denial of Service | partial-delete retry loop | low | accept | A permanently failing `DeleteHost` keeps the finalizer and requeues every 5 seconds, which blocks Kubernetes garbage collection of that route object until the server recovers or an operator patches the finalizer. That is the deliberate fail-closed tradeoff — the alternative is releasing the finalizer and orphaning live DNS entries. |

</threat_model>
