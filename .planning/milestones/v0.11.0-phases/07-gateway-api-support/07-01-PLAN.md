# Phase 7 Plan 01 — Tracer: HTTPRoute Hostname to Router DNS Entry

<objective>
Prove the whole Gateway API path end to end on one thin slice: a single
HTTPRoute with a single hostname, parented to a single Gateway that reports one
`IPAddress`-typed status address, becomes one router DNS entry — with the
finalizer and `host-ids` annotation lifecycle already in place.

Purpose: the architectural risk in this phase is the typed-route reconcile path
(typed `Get` per kind, `Gateway.status` read, annotation-tracked ownership). Prove
it on the agent's best early-context tokens before expanding to three kinds,
filtering, diffing, indexing, and CRD gating.
Output: `sigs.k8s.io/gateway-api v1.6.1` pinned and building; the annotation
helpers shared; `internal/operator/gateway_controller.go` with a working
HTTPRoute happy path; `cmd/operator/main.go` wired behind `--enable-gateway`.
</objective>

<task type="checkpoint:decision" gate="blocking">
  <decision>Confirm the Gateway route cleanup finalizer string before it is written to live cluster objects: `router-hosts.fzymgc.house/gateway-cleanup` (CONTEXT D-09).</decision>
  <context>
This is a one-way door. The next task writes this exact string onto every
HTTPRoute (and later GRPCRoute/TLSRoute) the operator reconciles. Once a release
carrying it reaches a user cluster, live route objects hold that finalizer.
Renaming it afterwards does not migrate anything: the old finalizer stays on every
existing route, no controller recognises it, and Kubernetes blocks deletion of
those routes until a human patches each one by hand. There is no automated undo.

The name follows the two finalizers already shipped — `router-hosts.fzymgc.house/host-cleanup`
(hostmapping_controller.go:27) and `router-hosts.fzymgc.house/ingressroute-cleanup`
(ingressroute_controller.go:29) — and is deliberately distinct from both so the
three controllers never contend for the same finalizer.
  </context>
  <options>
    <option id="confirm-gateway-cleanup">
      <name>Keep `router-hosts.fzymgc.house/gateway-cleanup` (D-09 as recorded)</name>
      <pros>Consistent with the two shipped finalizers; one finalizer per controller; already the locked decision; no further deliberation cost.</pros>
      <cons>A single finalizer covers all three route kinds, so a future decision to give TLSRoute its own cleanup semantics would need a second finalizer added alongside this one.</cons>
    </option>
    <option id="per-kind-finalizers">
      <name>Use per-kind finalizers (`.../httproute-cleanup`, `.../grpcroute-cleanup`, `.../tlsroute-cleanup`)</name>
      <pros>Each route kind's cleanup is independently retirable later without stranding the others.</pros>
      <cons>Three strings instead of one, three RBAC/doc surfaces, and no current requirement distinguishes cleanup by kind — the reconciler logic is identical across kinds. Diverges from the locked D-09.</cons>
    </option>
  </options>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Go module proxy → build | Third-party module source enters the binary at `go get` time |
| Kubernetes API server → operator | Route and Gateway objects are attacker-influencable by anyone with create rights in any watched namespace |
| operator → router-hosts gRPC server | Host mutations cross an mTLS boundary into the authoritative DNS store |
