# Phase 7 Plan 06 — Helm Chart, RBAC, and Documentation

<objective>
Ship the deployment surface for Gateway API support: RBAC that is sufficient but
least-privilege, an opt-in chart value, and documentation that names the cluster
prerequisite the chart deliberately does not bundle.

Purpose: GW-03 is exactly this. Without the ClusterRole rules the controllers
start and then fail every List/Watch; without the chart value there is no
supported way to turn the feature on.
Output: two new rule blocks in `clusterrole.yaml`, a conditional arg in
`deployment.yaml`, a `gateway:` block in `values.yaml`, and README coverage.

This plan touches only chart and documentation files, so it runs in wave 1 in
parallel with the Go work — Helm templates are not compiled against the binary.
</objective>

## Verification is manual, by design

`helm` v4.2.3 is available on the build host but is **not** wired into
`Taskfile.yml` — there is no `helm lint` step in `task lint` and no chart test
infrastructure in this repo, and `task manifests` regenerates only CRDs and
deepcopy code for `api/operator/...`. The `helm` commands in each task's `<verify>`
are real, runnable commands, but they are **not** part of `task ci`. Do not claim
an automated chart gate exists. Likewise, the `+kubebuilder:rbac` markers on the
reconciler (added in plan 01) are documentation-only in this repo — they drive no
generation step, so `clusterrole.yaml` is hand-maintained here exactly as the
existing Traefik and HostMapping rules already are.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Helm chart → Kubernetes RBAC | The ClusterRole this chart ships is the operator's entire authorization envelope against the API server |
| Chart values → operator runtime behavior | `gateway.enabled` is the only supported switch that lets the operator write DNS entries from Gateway API routes |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-07-03 | Elevation of Privilege | `clusterrole.yaml` Gateway API rules (ASVS V4 Access Control) | high | mitigate | Two separate rules with different verb sets: write verbs (`update`, `patch`) only on the three route kinds, justified by the finalizer and annotation write-back; `gateways` is read-only (`get`, `list`, `watch`). No `create`, no `delete`, no `*/status` subresource. Verified by rendering the chart and asserting the exact verb lists. |
| T-07-16 | Elevation of Privilege | `rbac.create=false` path | medium | mitigate | The new rules sit inside the existing `{{- if .Values.rbac.create -}}` guard, so an operator who manages RBAC out of band still gets no chart-created ClusterRole. Asserted by rendering with `rbac.create=false` and confirming no `gateway.networking.k8s.io` text appears. |
| T-07-17 | Tampering | chart-rendered `--enable-gateway` arg | medium | mitigate | The arg is rendered only under `.Values.gateway.enabled`, which defaults to `false`, so a chart upgrade cannot silently start writing router DNS entries on a cluster that merely has Gateway API CRDs installed. Asserted by rendering with default values and confirming the flag is absent. |

</threat_model>
