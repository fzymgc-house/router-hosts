# Phase 1 Plan 07 — Client Sink CLI — watch, Status File, Reconnect

<objective>
Turn the one-shot `render` path into a sink: a long-lived local process that keeps a
consumer's artifact current, survives connection loss, reloads the consumer's
resolver, and reports its own health both upstream and to a local file.

Purpose: the 0.10.12 failure mode #364 was filed over is a silently stale but
structurally valid zone. D-12 makes staleness visible through the marker and metrics
and never through a truncated or removed artifact — this plan is where that promise
is kept.
Output: `router-hosts watch`, the sidecar status file, and the post-write exec hook.

**Revised 2026-07-31 after cross-AI review** (`01-REVIEWS.md`).

**H3 — the pre-review plan's failure guarantee was impossible.** It said hook errors
follow the same path as render and write errors and leave the artifact untouched.
They cannot: by the time the hook runs, the artifact has already been replaced.
CONTEXT D-12a resolves this into **three** distinct outcomes, and the middle one is
the operationally important one — "your zone file is correct but your resolver did
not pick it up" is a different page from "your zone file is old". The artifact is
**never rolled back after the hook has run**, because on hook failure it is unknown
whether the resolver already read the new file, so reverting could leave the on-disk
file and the running resolver actively disagreeing. This plan therefore needs a
reload-health field, not a reinterpretation of the existing error field.

**H4 — the status ticker read last-success and failure state while the receive loop
wrote it, with no ownership model stated.** The suite runs under `-race`, so that is
a build-breaking gap, not a theoretical one. Ownership is now explicit: one
mutex-guarded type owns the state and serves immutable snapshots, matching the
locking discipline `hookrunner.go` already uses in this repo.

**TMPL-08** adds the client half of change identity: record the change ID that was
rendered, report it upstream, and skip a redundant render when it repeats — the
permitted half of D-21.

**Revised 2026-08-01 after cross-AI review round 2** (`01-REVIEWS.md` H4, H5, M3, M4,
M5, L2, L13).

**H4/H5/L13/M5 — one decision resolves four findings, and REVIEWS.md names it as such.**
The round-1 plan asked for package-level backoff variables that tests would mutate, and
for a `runWatch(...) error` contract. Both are broken. The e2e package is `e2e_test`
(`e2e/helpers_test.go:3`), an *external* test package, so it cannot reach unexported
variables in `internal/client/commands` at all — plan 08's restart test would not
compile (H4). And a `runWatch` that returns only an error tells the supervisor when a
session **ended**, never that it **succeeded**, so "reset the backoff as soon as a
session successfully completes a snapshot write" cannot be implemented: a session
normally keeps running after that write and may fail later (H5). Separately, jitter
drawn from package-level `math/rand` makes backoff tests non-deterministic (L13), and
the status ticker owning `stream.Send` can outlive the session while blocked (M5).

Codex's cross-plan suggestion is adopted: **one exported, injectable watch runtime
policy** covering backoff bounds, jitter and ticker interval, accepted by a testable
command constructor, with **no mutable production globals**. `runWatch` additionally
returns a structured session result carrying whether a snapshot was written, and the
session gets its own cancellable context so the ticker cannot survive it. Plan 08
consumes the same seam from outside the package.

**M3 — the sidecar was written and never read.** The round-1 plan describes the opening
status message as reporting "the state it already has on disk", but a fresh process
starts with an empty `sinkHealthState`, so after a consumer restart it reports no
rendered change ID, the server sees it as unconverged, and the first snapshot rewrites
and reloads an artifact that was already correct — a resolver reload on every restart
for no reason. Startup now loads the sidecar.

**M4 — a failed reload could never retry.** After a hook failure the artifact carries
the current change ID, so the very next snapshot matches and the D-21 skip fires,
suppressing the retry. `reload_failed` could then stay true until host state happened
to change. The skip guard now excludes that case.

**L2 — the mtime assertion goes.** Modification-time comparison is flaky on coarse
filesystem granularity, and the hook-invocation count already proves the skip.

## Revised 2026-08-01 after cross-AI review round 3 (`01-REVIEWS.md` M2, M3, L4)

**M2 — `WatchPolicy.StatusInterval` and the `--status-interval` flag had no defined
precedence, which makes the e2e seam inert.** The round-2 plan gives the policy a
status interval *and* specifies a Cobra flag with a fixed 30-second default. Cobra
writes its default into the bound variable whenever the flag is not set, so unless the
flag's default is *derived from* the injected policy, plan 08's
`WithWatchPolicy(WatchPolicy{StatusInterval: 50 * time.Millisecond, ...})` is
overwritten by 30 seconds and the external test cannot control ticker timing at all.
Precedence is now stated explicitly and asserted: **the resolved policy supplies the
flag's default value, and an explicitly-changed flag overrides the policy.**

**M3 — a blocked ticker `Send` needs an observable completion path.** Per-session
cancellation is correct and stays, but nothing in the round-2 plan required `runWatch`
to confirm the ticker goroutine had exited before returning, while
`TestWatch_StatusTickerStopsWithSession` implies exactly that seam. A small
completion channel closed by the ticker on return, awaited by `runWatch` after the
session cancel, is sufficient — and it does not violate single-send ownership, because
the channel carries no stream operation.

**L4 — advisory, and deliberately NOT acted on.** pi observed that
`TestWatch_LoadsSidecarAtStartup`'s artifact-deleted half is heavier than its marginal
coverage. **Rejected, with rationale, and both halves are retained.** The two halves
exercise two *different* `os.Stat` sites: the startup-adoption guard in step 1a (should
the loaded `rendered_change_id` be adopted at all?) and the in-cycle skip guard in step
3b (should this snapshot be skipped?). `TestWatch_RendersWhenArtifactMissingDespiteSameChangeID`
covers only the second. Dropping the artifact-deleted half would leave the startup
adoption guard with no test, and that guard is the one whose failure mode is permanent:
a sidecar asserting a rendered state that is not on disk makes the skip fire forever.
The cost is one extra fixture in an existing test; the coverage it buys is a
non-self-healing failure. Recorded here rather than in a review file so a later reader
does not "clean it up".

  <behavior>
- Writing a status record produces a file whose parsed contents carry the last-success time, the last error text, the consecutive-failure count, the contract version, the rendered change ID, the reload-failed flag and the last-reload-success time.
- A successful cycle clears the previous error text and resets the failure count to zero.
- A render or write failure preserves the previous last-success time, preserves the previous rendered change ID, and increments the failure count.
- A hook failure records the NEW last-success time and the NEW rendered change ID — the artifact was written — while setting the reload-failed flag and the error text, and does NOT increment the write-failure count.
- A subsequent successful hook clears the reload-failed flag and sets a last-reload-success time.
- The status file is written through the shared atomic writer, so a reader never sees a partial record.
- When no explicit status path is given, the default path is the artifact path with a status suffix appended.
- Concurrent readers and writers of the health state produce no data race under `-race`, and a reader observes a self-consistent record rather than a torn mix of two cycles.
- A post-write hook that exits zero returns no error.
- A post-write hook that exits non-zero returns an error naming the exit status.
- A post-write hook that outruns its timeout returns an error that identifies the failure as a timeout rather than as a non-zero exit.
- An empty hook command is a no-op returning no error.
- Reading a sidecar file written by `writeSinkStatus` returns the same record it wrote.
- Reading a sidecar path that does not exist returns the zero record and no error — a first run is not a failure.
- Reading a sidecar whose contents are not valid JSON returns an error, and the caller treats the state as unknown rather than trusting a partial parse.
- `DefaultWatchPolicy()` reports a 1 second initial backoff, a 60 second maximum, a 30 second status interval, and a non-nil jitter function.
- A policy whose jitter function is nil is normalised to the identity function rather than panicking, so a partially-populated policy from a test is safe.
- `defaultJitter` returns a duration between half and one and a half times its input.

1. `internal/client/commands/sinkstatus.go` — define
`type sinkStatus struct` with JSON-tagged fields `last_success` (RFC 3339 string
or a `time.Time`), `last_error` (string), `consecutive_failures` (int),
`contract_version` (string), `rendered_change_id` (string), `reload_failed` (bool)
and `last_reload_success` (RFC 3339). The last three exist because of D-12a and
D-18: an operator reading this file must be able to tell "my zone file is old"
from "my zone file is current but my resolver did not reload", and must be able to
say which server state the artifact represents. Provide
`func defaultStatusPath(artifactPath string) string` returning the artifact path
with `.status` appended, and `func writeSinkStatus(path string, st sinkStatus) error`
that marshals with `json.MarshalIndent`, appends a trailing newline, and writes via
`atomicfile.Write`. Wrap every error with `oops.Wrapf`.

Add the read half, which the round-1 plan omitted (review M3):
`func readSinkStatus(path string) (sinkStatus, error)`. Return the zero `sinkStatus`
and a **nil** error when the file does not exist (`errors.Is(err, os.ErrNotExist)`) —
a first run is not a failure. Return a wrapped error for any other read failure or for
JSON that does not parse, so a corrupt sidecar is reported rather than silently
treated as "never rendered". Document that the caller must not trust
`rendered_change_id` unless the artifact itself still exists, because the two files
are written separately and one can outlive the other.

The status file exists specifically for the server-down case: when the server is
unreachable, server-side metrics are unavailable by definition while sinks keep
serving their last-good artifacts, so this file is then the only health signal.
Record that rationale in the file's doc comment.

2. **Define the ownership model before any concurrent code exists** (review H4).
In the same file, add
`type sinkHealthState struct { mu sync.Mutex; st sinkStatus }` with:

- `func (s *sinkHealthState) recordSuccess(changeID string, at time.Time)` —
  sets `last_success` and `rendered_change_id`, clears `last_error`, zeroes
  `consecutive_failures`. Outcome one of D-12a.
- `func (s *sinkHealthState) recordReloadFailure(err error, at time.Time)` —
  called **after** a successful write whose hook then failed. Sets
  `reload_failed` and `last_error`, and leaves `last_success`,
  `rendered_change_id` and `consecutive_failures` exactly as `recordSuccess` just
  set them. This is D-12a's middle row and it is the whole reason reload health is
  a separate field: collapsing it into the failure count would make a
  correct-file-stale-resolver look identical to a stale file.
- `func (s *sinkHealthState) recordReloadSuccess(at time.Time)` — clears
  `reload_failed`, sets `last_reload_success`.
- `func (s *sinkHealthState) recordFailure(err error)` — increments
  `consecutive_failures`, sets `last_error`, and preserves `last_success` and
  `rendered_change_id`. Outcomes one and three of D-12a (render/write failure and
  connection loss).
- `func (s *sinkHealthState) snapshot() sinkStatus` — returns a by-value copy under
  the lock.

Document at the type that this is the **single owner** of every field shared
between the receive loop, which writes, and the status ticker, which reads; that
the ticker and the sidecar writer obtain state only through `snapshot()`; and that
no caller may hold a pointer into it. `sinkStatus` must stay a value type with no
reference-typed fields so the copy is a real copy. The repo's existing
shared-state code (`hookrunner.go`) uses explicit locking and the suite runs
`-race`, so this is the house style, not an invention.

3. **Do not roll back the artifact on hook failure, ever.** State this in the
package doc comment beside the outcome table. On hook failure it is unknown
whether the resolver already read the new file; reverting could leave the on-disk
file and the running resolver actively disagreeing, which is strictly worse than
retaining a correct file whose reload failed. Retention plus a distinguishable
health signal is the contract.

5. **`internal/client/commands/watchpolicy.go` (new) — the injectable runtime policy

`type WatchPolicy struct { InitialBackoff time.Duration; MaxBackoff time.Duration;

with `func DefaultWatchPolicy() WatchPolicy` returning 1s, 60s, 30s and
`defaultJitter`, and `func defaultJitter(d time.Duration) time.Duration` multiplying

The type is **exported and passed by value**. That is the whole point: `e2e` is an
external test package (`e2e/helpers_test.go:3` declares `package e2e_test`) and cannot
touch unexported identifiers in `internal/client/commands`, so plan 08's restart test
would not compile against package-level backoff variables. Document on the type that
it exists so timing can be injected, that production callers use
`DefaultWatchPolicy()`, and that `InitialBackoff`, `MaxBackoff` and `Jitter` are
deliberately **not** CLI flags or TOML keys — each would be a permanent compatibility
surface for a tuning need nobody has expressed.

**`StatusInterval` is the one exception, and its precedence must be written down here
(review round-3 M2).** It *is* an operator-facing flag (`--status-interval`), so two
sources of truth exist for the same value and Cobra will silently win unless told
otherwise: `Flags().DurationVar(&v, "status-interval", 30*time.Second, ...)` writes 30
seconds into the bound variable whenever the flag is absent, overwriting whatever the
injected policy said, and plan 08's millisecond-interval e2e seam would then be inert
with nothing failing to indicate it.

The rule, stated on the field's doc comment and implemented in `newWatchCmd`:
**the resolved policy supplies the flag's default, and an explicitly-changed flag
overrides the policy.** Concretely — register the flag with
`policy.normalized().StatusInterval` as its default value rather than a literal
`30 * time.Second` (so `DefaultWatchPolicy()`'s 30 seconds remains the production
default and no observable behavior changes), and after parsing, take the flag's value
only when `cmd.Flags().Changed("status-interval")` is true, otherwise take
`policy.StatusInterval`. The `Changed` check is what makes "an operator asked for this"
distinguishable from "Cobra filled in a default", which is the whole ambiguity. Record
that reasoning at the resolution site.

Document on `Jitter` why it is a function field rather than an inline `math/rand`
call (review L13): a backoff test that must assert an exact wait cannot do so against
package-level randomness, and injecting the identity function makes the schedule
deterministic without weakening production behavior. Note that `math/rand` is correct
here and `crypto/rand` is not needed — this is scheduling jitter to break lockstep
reconnects, not a security decision — and if a linter objects, document the reason
rather than adding a suppression directive.
