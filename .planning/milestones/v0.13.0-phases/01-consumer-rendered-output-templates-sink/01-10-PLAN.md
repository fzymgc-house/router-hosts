# Phase 1 Plan 10 — Honor the explicit `--config` path in the client (gap G-01-1)

<objective>
Close gap G-01-1's plumbing half: make `--config <path>` actually select the client
config file, and make an unreadable explicit path a loud error instead of a silent
fall-through to XDG auto-discovery.

Purpose: `Flags.Config` is registered at `internal/client/commands/root.go:88` and read
nowhere in the repo. `config.LoadClientConfig` resolves its file layer solely through
`findClientConfigFile()`, an XDG/platform directory search. The user-visible consequence,
observed during phase 01 UAT: `router-hosts watch --config <path>` dialed the operator's
production router with the operator's production client certificate instead of the
127.0.0.1:18443 named in the file passed to `--config`. Wrong server, wrong credentials,
sidecar still reporting healthy. This is the wrong-target-mTLS threat in the threat model
below, not a cosmetic flag bug.

This is the leading, thinnest end-to-end slice of the two-plan gap closure: Task 1 wires
one path through every layer of the seam (cobra flag to command to config loader) and
proves it with a test demonstrated RED first. Plan `01-11` then observes this fix from a
real OS process, which is the only vantage point from which the bug was ever visible.

Output: `ClientConfigOverrides.ConfigPath`, the layer-1 explicit-path branch, eleven
regression tests, and updated `--config` documentation.

Scope note: `serve --config` is a separate, already-correct path
(`internal/client/commands/serve.go:29` passes its own `configPath` straight to
`config.LoadServerConfig`). Nothing in this plan touches it.
</objective>

<threat_model>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| operator intent to resolved client config | The operator names a target server and a credential set; a defect here substitutes a different, unnamed target and credential set with no signal |
| client to gRPC server (mTLS) | The resolved config decides which endpoint is dialed and which client certificate and CA are presented; both are attacker-relevant if mis-resolved |
| ambient environment (XDG dirs, env vars) to config resolution | Files the invoking command never named can influence, or before this fix entirely determine, the connection target |

ASVS level 1. Blocking threshold: `high`.

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-G1-01 | Spoofing | `config.LoadClientConfig` file layer | critical | mitigate | An explicit `--config` path is loaded directly (Task 1); the ambient XDG search cannot substitute a different endpoint for the one the operator named. Pinned by `TestLoadClientConfig_ExplicitPathBeatsXDG` and, at process level, by plan 01-11's two-server discrimination test |
| T-01-G1-02 | Information Disclosure | client mTLS credential selection | high | mitigate | Because the endpoint and the certificate paths come from the same file layer, a mis-resolved config presents the operator's client certificate to an unintended server. | T-01-G1-03 | Tampering | cross-layer config merge | high | mitigate | An explicit load replaces the file layer wholesale rather than merging, so no `cert_path`, `key_path`, or `ca_cert_path` from an unrelated discovered config survives. Task 2's anti-merge test is the gate |
| T-01-G1-04 | Repudiation | silent fallback on unreadable path | high | mitigate | An unreadable or unparseable explicit path returns an `oops`-wrapped error naming the path (Task 1) instead of proceeding.
