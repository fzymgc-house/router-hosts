# Phase 9 Plan 01 — Tracer: Detached Hook Run with a Resolved Timeout and a Recorded Metric

<objective>
Prove the whole Phase 9 architecture end-to-end on one thin path: a single configured
`on_success` hook, with a per-hook timeout resolved from TOML, executed by a detached
background runner against a server-lifecycle context, recording a real OTel execution
metric — while `regenerateOutputs` returns before that hook finishes.

Purpose: this is the tracer slice. Every layer the phase touches (config schema →
executor → runner → gRPC service → `serve.go` wiring) is wired for keeps in one commit,
so an architectural dead-end surfaces now rather than after four expansion plans have
landed. Later plans expand horizontally from this proven path (status classification,
coalescing counter, the `default_timeout` middle link, drain semantics, docs).

Output: a working detached hook path with metrics, plus the migrated existing tests that
prove the tree stays green.
</objective>

<assumption_delta_decision>
**Promoted noun:** the per-hook *effective timeout*.

**Decision:** `promote` (not `add-alongside`).

**What changed:** `defaultHookTimeout` in `internal/client/commands/serve.go:19-20` was a
constant. It becomes the last link in a resolution chain: per-hook `timeout` →
`[hooks] default_timeout` (Plan 09-02) → built-in `config.DefaultHookTimeout` (30s).

**Rationale:** the effective timeout is resolved ONCE — at config load and at executor
construction — and stored on each `config.HookDefinition` value the executor holds. At
execution time `executeHook` reads a single already-resolved duration off the hook and
no run-time code path consults a global default. The rejected `add-alongside` shape (the
executor keeps a default field and falls back per hook at execution time) would encode
the fallback rule in two places and let them drift.

**Enforcement:** the struct-level executor timeout field is REMOVED, not kept. The
invariant "every configured hook has a positive resolved effective timeout after config
load, for every combination of per-hook-set / default-set / neither" is encoded as a test
in Plan 09-02 (`TestHooksConfig_ResolveTimeouts_Invariant`).

**Backwards compatibility:** `NewHookExecutor`'s third positional parameter is retained
(renamed to `defaultTimeout`) and used *only* inside the constructor's resolution loop, so
all 12 existing `NewHookExecutor(...)` call sites in `internal/server/*_test.go` keep
compiling and keep their current behavior.
</assumption_delta_decision>

**internal/server/hookrunner.go (NEW)**

- `type hookRunRequest struct` with exactly three fields: `event string`,
  `entryCount int`, `errMsg string`. It MUST NOT carry a `context.Context` field — a
  stored RPC context would be cancelled when the gRPC handler returns and would race the
  just-detached hook run.
- `type hookRunner struct` holding: `exec *HookExecutor`, `log *slog.Logger`,
  `mu sync.Mutex`, `pending *hookRunRequest`, `stopped bool`, `trigger chan struct{}`
  (capacity 1), `ctx context.Context`, `cancel context.CancelFunc`, `quit chan struct{}`,
  `done chan struct{}`.
- `newHookRunner(exec *HookExecutor, logger *slog.Logger) *hookRunner` creates the base
  context with `context.WithCancel(context.Background())` — server lifecycle, never an
  RPC context — and makes `trigger` with capacity 1, `quit` and `done` unbuffered.
- `Start()` launches `go r.loop()`, mirroring `WriteQueue.Start`.
- `Trigger(req hookRunRequest)` takes the mutex, stores `&req` into `pending`
  (latest-wins — overwriting an existing pending value is the coalescing point that Plan
  09-04 instruments), releases the mutex, then does a non-blocking send on `trigger` with
  a bare `default:` branch. It MUST NOT block and MUST NOT touch hook I/O.
- `loop()` starts with `defer close(r.done)` and selects on `trigger` and `quit`, matching
  `WriteQueue.process`. On `trigger`: take the mutex, take `pending`, set `pending` to
  nil, release, and if non-nil call `runBatch`. On `quit`: drain the single pending
  request (run it if present) and return — the same drain-before-exit intent as
  `WriteQueue.process`'s buffered drain.
- `runBatch(req hookRunRequest)` dispatches on `req.event`: `"success"` calls
  `r.exec.RunSuccess(r.ctx, req.entryCount)`, otherwise
  `r.exec.RunFailure(r.ctx, req.entryCount, req.errMsg)`. The context passed is ALWAYS
  `r.ctx`.
- `Stop(ctx context.Context)` uses the `WriteQueue.Stop` mutex-guarded shape: under the
  mutex, if not already stopped, set `stopped` and `close(r.quit)`. Then
  `select { case <-r.done: case <-ctx.Done(): r.cancel(); <-r.done }`. Calling `Stop`
  twice must not panic.
- Log with `log/slog` key/value pairs using the existing `"hook"` / `"event"` key
  convention from `hooks.go`.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| operator config file → server process | `[hooks]` entries are shell command strings; the TOML file is the tamper surface, already guarded by `checkConfigPermissions` (rejects group/world-writable **because** it contains hook commands). |
| gRPC client → write RPC → hook runner | Untrusted client input drives host mutations, which now trigger a *detached* background hook batch. Only plain data (`event`, `entryCount`, `errMsg`) crosses the goroutine boundary. |
| server process → hook subprocess (`sh -c`) | The hook inherits the server's environment plus three `ROUTER_HOSTS_*` variables; `errMsg` is attacker-influenced text. |
| server process → OTel collector | Metric attribute values leave the trust boundary. |
