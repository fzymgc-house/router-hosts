<ci_02_note>
**On CI-02's wording.** CI-02 reads "the fast tier gates every PR; the container
and process tiers gate merge to `main`." Per locked decision D-03, that
two-stage reading collapses to a single PR-time gate in this repository, because
the mechanism the wording assumes does not exist here: `ci-go.yml` triggers only
on `pull_request` (plus the `workflow_dispatch` recovery path added by plan 01),
the `protect-main` ruleset has no `merge_queue` rule, and merges are squash-only.
All three tiers therefore run on every PR, and because the PR check *is* the
merge gate, nothing can reach `main` without all three green.

**The substance of CI-02 is satisfied; its wording describes a two-stage
mechanism this repository lacks.** A merge queue was considered and rejected as
its own phase's worth of work, and D-03 is forward-compatible with adding one
later — the fast/slow split can be re-introduced without undoing anything built
here.
</ci_02_note>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| PR author -> workflow definition | A PR can edit `ci-go.yml`, including removing its own gates |
| CI runner -> Docker daemon availability | The tier's meaningfulness depends on Docker actually being present on the runner |
| Go build cache -> `bin/` freshness | A cache that restored `bin/` would let `proc_e2e` test a stale binary |
| Aggregate job result -> `protect-main` required check | One context carries the entire merge-blocking signal |
