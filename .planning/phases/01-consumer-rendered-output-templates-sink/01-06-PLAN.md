# Phase 1 Plan 06 — Server-Side Sink Streaming — Change Notification and Follow Mode

<objective>
Make the `WatchHosts` stream a real sink: the server pushes a fresh, coalesced,
complete snapshot every time host data changes, while the consumer independently
reports its own health on the same open stream.

This is the highest-novelty work in the phase. `ImportHosts` is a false friend — it
drains every `Recv()` before its first `Send()`, so it proves the Go type signature
compiles here and nothing else. The concurrent goroutine pair is built fresh against
the grpc-go concurrency contract.

Purpose: TMPL-05 requires the artifact to stay current without polling, and D-06
requires bursts to coalesce.
Output: `changeNotifier`, follow mode on `WatchHosts`, and the server-side wiring
that connects change notification, sink health, and OTel.

**Revised 2026-07-31 after cross-AI review** (`01-REVIEWS.md`), and this plan carries
the review's strongest signal.

**H1 — both reviewers independently found the same teardown bug, by two different
paths.** The pre-review skeleton kept `stream.Recv` on the handler goroutine, then
did `cancel()`, `wg.Wait()`, and only then returned. Cancelling a context derived
from `stream.Context()` does not unblock a gRPC stream operation. Codex's path: if
`Send` fails while the client is silent, the sender exits but the handler stays
blocked in `Recv` forever. pi's path: if the sender is blocked inside `Send` on flow
control — a healthy but slow client — `wg.Wait()` never returns and the handler
never returns. Plan 04's keepalive bounds neither case, because in both the network
is alive. **The fix is structural and is specified below: the handler owns neither
direction, and it never joins.** `go doc google.golang.org/grpc.ServerStream` is
explicit that `SendMsg` blocks until "the stream is done, or the stream breaks", and
that `RecvMsg` blocks "until it receives a message into m or the stream is done" —
so returning from the handler, which ends the RPC, is exactly the thing that
unblocks both. Joining first is what removes that escape.

**M2 — the coalescing claim was stronger than the mechanism.** pi traced the
subscribe-before-send ordering and confirmed it is correct: a `Notify()` landing
mid-send closes the held generation channel, so no update is lost. That part is kept
verbatim. What was wrong was the *promise* and the *test*: closing a generation
channel coalesces only while a watcher is busy or has not resubscribed, so
`TestService_WatchHosts_FollowCoalescesBurst` asserting strictly fewer snapshots than
mutations encodes a race and will flake. The contract is restated precisely and the
assertion is replaced with deterministic ones.

This plan also picks up round-1 review L3 (record a status payload on the opening
message) and enforces the D-21 boundary — the server must never let a client-reported
change ID influence what it sends — with a dedicated test rather than a convention.

**Revised 2026-08-01 after cross-AI review round 2** (`01-REVIEWS.md` H1, M2, M9, L6,
L11).

**H1 — `sendSnapshot` inherits plan 01's derivation-order fix.** Follow snapshots share
the one-shot path's helper, so the change ID must be read **before** `store.ListAll`
here too. Without that, a mutation landing mid-snapshot produces a snapshot labelled
with an ID newer than its entries, and plan 07's D-21 client skip then pins that
consumer to the stale entry set permanently while its convergence gauge reads 1. Both
reviewers reached this from opposite directions; the full reasoning is in plan 01's
objective. This plan's job is to make sure the shared helper carries the fixed order
and that follow mode does not reintroduce the reversed one.

**M2 — notification no longer waits for the legacy generators.** `regenerateOutputs`
runs the hosts-file, dnsmasq and unbound generators — three potentially slow filesystem
writes — before the round-1 plan's notify site. That coupled every consumer's snapshot
latency to server-owned output that has nothing to do with it, and to any filesystem
failure in that path, which directly weakens the phase's independent-consumer goal.
Codex asked whether notification should move to fire on write commit instead. It
already effectively does: `regenerateOutputs` is called from `AddHost`, `UpdateHost`,
`DeleteHost`, `ImportHosts`, `RollbackToSnapshot` and startup, and in every case the
write has already committed before the call. So the fix needs no new call site and no
new notification plumbing — **`Notify()` becomes the first statement of
`regenerateOutputs`**, above the generator blocks rather than merely above the
`if s.hooks == nil || !ran` early return. One notify site still covers every mutation
path, the generator-less deployment is still covered (that was the round-1 concern, and
it is trivially satisfied when the call is first), and a consumer is now woken as soon
as the state it will read is durable.

**M9, L6, L11 — three smaller corrections.** The non-joining handler is the right
design but had no leak assertion, so a repeated connect/disconnect churn test is added
(M9). Task 1's `<done>` still said "exactly once per burst", contradicting the
coalescing contract the same task carefully restates (L6). And an unverifiable peer
identity now increments plan 05's identity-failure signal and logs at warn rather than
debug, so a broken authentication path cannot hide behind a rising connected count
(L11).
</objective>

**Handler shape (this is the H1 fix; implement it exactly).** In follow mode the
handler does five things and nothing else. It derives a cancellable context from
`stream.Context()` and defers the cancel. It creates an error channel of
**capacity 2** — the capacity is load-bearing, because both goroutines must be
able to report an error and exit even after the handler has already returned, and
an unbuffered channel would leak whichever one reported second. It spawns a sender
goroutine that is the sole owner of `stream.Send`. It spawns a receiver goroutine
that is the sole owner of `stream.Recv`. Then it blocks in a `select` over the
error channel and the context's done channel, and on either one it **returns
immediately** — returning the received error, or nil for a done context.

The handler must not wait for either goroutine before returning. Returning is
what ends the RPC, and ending the RPC is what unblocks the other goroutine.

Write a comment above that `select` recording *why* the handler does not join,
in these terms: `go doc google.golang.org/grpc.ServerStream` states that `SendMsg`
blocks until "there is sufficient flow control", "the stream is done", or "the
stream breaks", and that `RecvMsg` blocks until a message arrives or "the stream
is done". Cancelling a context **derived from** `stream.Context()` is none of
those things and unblocks neither call. Returning from the handler ends the RPC,
which is "the stream is done", and that is what releases a `Send` stalled on a
slow-but-healthy client and a `Recv` with nothing pending. Joining the goroutines
before returning removes the only mechanism that can unblock them, and deadlocks
in exactly two windows: a failed `Send` while the client is silent, and a blocked
`Send` when the client calls `CloseSend`. Keepalive does not rescue either case,
because the connection is alive in both.

Write that comment in prose. Do not name the join identifier in it — an
acceptance criterion below negative-greps this file for that identifier, so a
comment mentioning it by name fails the very gate that protects the design.

The handler goroutine must own neither direction. That is what lets it `select`
and return on the first error instead of sitting inside a blocking call, and it
preserves single ownership per direction, which is what the grpc-go contract
actually requires.

Read the opening request with a single `stream.Recv()` on the handler goroutine
**before** spawning either goroutine, so `follow` can be inspected and there is
never a concurrent second reader. If that opening request carries a status
payload, record it before spawning (review L3) — a reconnecting sink uses the
opening message to report what it already has on disk, and dropping it loses a
convergence signal at exactly the moment it is most useful.

Resolve the identity with `commonNameFromContext(ctx)`. On error (review L11): log at
**warn** level with `slog`, not debug, including the error and the peer address;
call `s.sinkHealth.RecordIdentityFailure()` when the registry is present; and proceed
with per-identity health recording disabled for this stream — never substitute a
caller-supplied value or an empty key. Warn rather than debug because the server sets
`tls.RequireAndVerifyClientCert` (`server.go:207`), so a connection cannot reach this
handler without a CA-verified chain: reaching this branch at all means something in
the authentication path is not behaving as designed, and it would otherwise be
invisible except as a connected count that exceeds the number of tracked identities.
Call
`s.sinkHealth.Connect()` and `defer s.sinkHealth.Disconnect()` **unconditionally**
when the registry is present, because that counter carries no label and needs no
identity; the deferred `Disconnect` running on handler return is also the
observable the teardown tests assert on.

The sender's loop order is load-bearing and must be exactly: take
`ch := s.changes.Subscribe()`; send a snapshot; then `select` on `ctx.Done()` and
`<-ch`; on wake, take a fresh subscription and loop. Subscribing before reading
state is what guarantees a mutation landing during a send is not lost — pi traced
this and confirmed it correct, so do not "simplify" it. Taking the newest channel
on wake is what collapses a burst. Write a comment at the loop head stating both
properties, because reordering these two lines produces a silent lost-update bug
that no compiler will catch.

The receiver loop calls `stream.Recv()`, treats `io.EOF` as a clean client hangup
(report nil to `errCh` and return), and on a message carrying a status payload
calls `s.sinkHealth.RecordStatus(cn, ...)` with the reported fields mapped into
plan 05's `SinkState` — converting reported Unix seconds to `time.Time` and
treating 0 as the zero time rather than 1970, and copying `rendered_change_id`,
`reload_failed` and `last_reload_success_unix` straight through. Any other receive
error is reported to `errCh` and ends the loop.

**D-21 is a hard boundary and this is the file where someone will cross it.** The
handler records `rendered_change_id` and does nothing else with it. Nothing in the
sender may read a client-reported change ID, compare against it, or use it to skip

the permitted half of the same optimization. State that at the recording site, and
note that the forbidden half is a natural-sounding efficiency win someone will
