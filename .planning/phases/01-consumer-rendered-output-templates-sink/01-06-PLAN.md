# Phase 1 Plan 06 — Server-Side Sink Streaming — Change Notification and Follow Mode

<objective>
Make the `WatchHosts` stream a real sink: the server pushes a fresh, coalesced,
complete snapshot every time host data changes, while the consumer independently
reports its own health on the same open stream.

This is the highest-novelty work in the phase. `ImportHosts` is a false friend — it
drains every `Recv()` before its first `Send()`, so it proves the Go type signature
compiles here and nothing else. The concurrent goroutine pair is built fresh against
the grpc-go concurrency contract.

Purpose: TMPL-05 requires the artifact to stay current without polling, and D-06
requires bursts to coalesce so a watcher never renders an intermediate state.
Output: `changeNotifier`, follow mode on `WatchHosts`, and the server-side wiring
that connects change notification, sink health, and OTel.
</objective>

  <behavior>
- A follow request receives a complete snapshot immediately, before any mutation occurs.
- After a host is added, the follow stream receives a further complete snapshot containing that host, with no polling and no client request in between.
- Each snapshot is the full entry set followed by exactly one terminator, identical in shape to the one-shot response sequence.
- A rapid burst of mutations produces fewer snapshots than mutations, and the last snapshot received reflects the final state.
- A client status message sent mid-stream updates that consumer's health record without interrupting snapshot delivery.
- When the client closes the stream, the handler returns without error and the health record for that consumer persists.
- When peer identity cannot be verified (for example over a non-TLS test connection), snapshots still stream and no health record is created.
- Cancelling the stream context terminates both goroutines and the handler returns promptly.
  </behavior>
  <action>
Build the goroutine pair from scratch. Do not adapt `ImportHosts`.

1. `internal/server/service.go` — add a `sinkHealth *SinkHealth` field to
`HostsServiceImpl` and a `func WithSinkHealth(health *SinkHealth) ServiceOption`
constructor beside the existing option constructors at lines 49-84. Leave the
field nil-tolerant: every use site must check for nil, because the bufconn test
harnesses construct the service without it.

2. `internal/server/watch.go` — replace the Unimplemented branch. Extract the
one-shot body into an unexported helper, e.g.
`func (s *HostsServiceImpl) sendSnapshot(ctx context.Context, send func(*hostsv1.WatchHostsResponse) error) error`,
so the one-shot path and every follow-mode push share one implementation and the
terminator can never drift between them.

For follow mode: derive `ctx, cancel := context.WithCancel(stream.Context())` and
`defer cancel()`. Resolve the identity with `commonNameFromContext(ctx)`; on
error log at debug or warn level with `slog` and proceed with health recording
disabled for this stream — never substitute a caller-supplied value or an empty
key. When both the identity and `s.sinkHealth` are available, call
`RecordConnected` and `defer RecordDisconnected`.

Spawn exactly one goroutine that owns `stream.Send` and keep `stream.Recv` on the
handler's own goroutine — the grpc-go contract permits one sender and one
receiver concurrently and forbids two of either. Coordinate with a
`sync.WaitGroup` and a buffered `chan error` of capacity 2; the first error from
either side cancels the shared context.

The sender's loop order is load-bearing and must be exactly: take
`ch := s.changes.Subscribe()`; send a snapshot; then `select` on `ctx.Done()` and
`<-ch`; on wake, take a fresh subscription and loop. Subscribing before reading
state is what guarantees a mutation landing during a send is not lost, and taking
the newest channel on wake is what collapses a burst into one snapshot. Write a
comment at the loop head stating both properties, because reordering these two
lines produces a silent lost-update bug that no compiler will catch.

The receiver loop calls `stream.Recv()`, treats `io.EOF` as a clean client
hangup, and on a message carrying a status payload calls
`s.sinkHealth.RecordStatus(cn, ...)` converting the reported Unix seconds to a
`time.Time` (treat 0 as the zero time, not as 1970). Any other receive error
cancels the context and ends the loop.

After the receiver ends: cancel, `wg.Wait()`, then drain the error channel
non-blockingly and return the first error, or nil.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| consumer stream to server goroutines | Each connected sink causes the server to hold a goroutine, a subscription and a periodic full read of the projection |
| consumer status message to server state | Untrusted request-body content updates a per-consumer record |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-1-19 | Denial of Service | many concurrent sinks each triggering a full `store.ListAll` fold on every mutation | medium | mitigate | Coalescing bounds the work per watcher to one read per change burst rather than one per mutation; snapshots are pushed only on real changes, never polled. The residual per-watcher cost is proportional to connected, CA-authenticated consumers, which is the same bound the metric cardinality has. |
| T-1-20 | Denial of Service | goroutine or subscription leak on stream teardown | high | mitigate | The handler derives a cancellable context from the stream, cancels it on every exit path, and joins the sender with a `WaitGroup` before returning. `TestService_WatchHosts_FollowContextCancelReturns` proves both goroutines exit, and repeated race-detector runs cover the teardown ordering. |
| T-1-21 | Tampering | a stream driven into a lost-update state by a mutation landing mid-send | high | mitigate | Subscribe-before-read ordering in the sender loop, documented at the call site and covered by `TestService_WatchHosts_FollowPushesOnMutation` and `TestService_WatchHosts_FollowCoalescesBurst`. |
| T-1-22 | Spoofing | health recorded against an identity the caller chose | high | mitigate | The identity comes only from `commonNameFromContext`; when it is unavailable the handler records nothing rather than falling back to a request field or an empty key, asserted by `TestService_WatchHosts_FollowWithoutPeerIdentityStillStreams`. |
| T-1-23 | Denial of Service | concurrent `Send` from two goroutines corrupting the stream | high | mitigate | Exactly one goroutine is spawned and it is the sole owner of `stream.Send`; the handler goroutine is the sole owner of `stream.Recv`. This matches the quoted grpc-go concurrency contract and is asserted by a goroutine-count criterion plus repeated race-detector runs. |
| T-1-SC | Tampering | npm/pip/cargo installs | high | mitigate | Not applicable: no new external packages and no package-manager install task exists in this plan. |
