# Phase 1 Plan 09 — Change-ID Storage Foundation: Commit-Ordered Event IDs and `LatestEventID`

<objective>
Establish the storage-layer premise TMPL-08 rests on, before any plan derives a change
ID from it: an event log in which no commit can land an ID at or below the log's
current maximum, and a `LatestEventID` read that returns that maximum.

Purpose: `MAX(event_id)` is a valid change ID **only** if no commit can insert an ID
that sorts below an ID already in the log. That is currently false.
Output: `internal/eventid` (a monotonic generator with a persisted-log floor), an
in-transaction ordering guard at the single funnel for all post-migration appends,
`storage.EventStore.LatestEventID`, `storage.ZeroChangeID`, and deterministic
regression tests for compaction, restart, a caller-supplied lower ID, a zero ID into
an empty store, and reverse-order concurrent commits.

**Created 2026-08-01 in response to cross-AI review round 2** (`01-REVIEWS.md` H2).
Codex checked the claim the round-1 revision made and found it false in the repo
today: `internal/storage/sqlite/eventstore.go:258` mints the `HostCompacted`
replacement seed with a bare `ulid.Make()` inside `CompactAggregate`, bypassing
`CommandHandler.newID` (`internal/server/commands.go:60`) and the shared
`*ulid.MonotonicEntropy` entirely.

The consequence is precisely the failure D-20 exists to prevent. A same-millisecond
bare ULID can sort **below** the maximum it replaces, so a compaction can leave
`MAX(event_id)` pinned or move it backward — the change ID fails to advance across a
real state change and a deduping consumer silently keeps serving a stale zone. D-22
anticipated compaction moving the ID *forward* and accepted one redundant render; it
did not anticipate it moving *backward*.

## Revised 2026-08-01 after cross-AI review round 3 (`01-REVIEWS.md` H2, H3, H4, M4, M7, L3)

**Round 3 adjudicated the round-2 remedy insufficient, and the adjudication is
correct.** Routing both known mint sites through one process-wide monotonic generator
does not establish the invariant this plan asserted. Three separate gaps, all closed
here by one mechanism.

**H2 — mint order is not commit order, and this is the serious one.** Event IDs are
minted **outside** the write-queue lock in every command. `internal/server/commands.go:115`
(`id := h.newID()`) and `:119` (`newEnvelope`, which mints `EventID` at `:77`) both run
**before** `h.submitWrite(...)` at `:135`; the same shape repeats at `:201-268` before
`:284`, and `:345` before `:354`. Only the duplicate check and the store write execute
inside the queue. So: goroutine A mints ID_A; goroutine B mints ID_B greater than ID_A;
B wins the queue and commits, leaving the log maximum at ID_B; A then commits an ID
that sorts **below** an ID already in the log, and `MAX(event_id)` does not advance
across A's commit. A consumer holding ID_B computes the same change ID, the D-21 skip
fires, and A's mutation is never rendered. No restart and no clock anomaly is required
— ordinary concurrent writes reach it.

**H3 — the generator is process-local**, so an ID minted immediately after a restart,
inside the same millisecond as the last pre-restart append, can sort below it. The
round-2 plan documented this as accepted while *also* asserting an unqualified "no
append path can produce an ID that sorts below an ID already in the log". That
contradiction was the defect independent of any remedy.

**H4 — the storage boundary accepts caller-constructed envelopes.**
`AppendEvent`, `AppendEvents` and `AppendEventsBatch` all take a
`domain.EventEnvelope` the caller built (`internal/storage/storage.go:51`), so routing
two known production sites through a shared generator cannot make an interface-level
guarantee true.

**The user's decision, implemented here: seed the generator from `LatestEventID` at
storage startup, AND re-check the proposed event ID against `MAX(event_id)` inside the
append transaction.** The in-transaction check is the load-bearing half — it makes
mint order irrelevant, which no process-local generator can achieve — and it closes
H2, H3 and H4 together. `internal/storage/sqlite/eventstore.go:313` `insertEvent` is
the single funnel for all post-migration appends: `AppendEvent` (`:21`),
`AppendEvents` (`:55`), `AppendEventsBatch` (`:93`) and `CompactAggregate` (`:210`)
all route through it, and every one of them calls it inside a
`sqlitex.ImmediateTransaction`, so one guard there covers every append path including
a caller-constructed envelope. (Round-4 M1 corrected this plan's earlier unqualified
phrasing — see the round-4 section below for the one INSERT statement that does not
funnel through `insertEvent` and why that is bounded.)

**The rejected alternative, recorded so it is not re-proposed:** a database-owned
monotonic sequence assigned in the append transaction. It is a stronger mechanism, but
D-18 fixes the change ID as *the ULID of the newest event* and the proto carries it as
a ULID string. Adopting a sequence means a schema migration, a wire-type change, and an
amendment to a locked decision. **D-18 and D-19 are unchanged by this plan, there is no
schema migration, and the wire type stays a ULID string.** The prohibition is recorded
in `must_haves.prohibitions`.

**The invariant this plan now claims is the one the mechanism actually delivers:** not
"every ID is minted monotonically" (unachievable across processes and arbitrary
callers) but "**no commit lands an ID at or below the log maximum**". Mint order is
allowed to be arbitrary; commit order is what the guard makes authoritative.

**A note on CONTEXT.md D-20.** D-20's *mandate* — any change to ID generation must
preserve monotonicity — is exactly what this plan implements. D-20's *rationale* text
contains a factual error about the current code (it says every append path mints
through `newID()`, which is false both for compaction at `eventstore.go:258` and for
the mint-versus-commit ordering above). **Do not repeat that claim anywhere in code
comments, doc comments, or the SUMMARY.** CONTEXT.md is not edited by this plan — it
records locked user decisions and the discrepancy is being surfaced to the user
separately.

**M4, M7, L3 — three smaller round-3 items.** `mu sync.Mutex // protects entropy`
(`commands.go:23`) exists solely to guard the field being removed and must go with it.
The compaction regression test is probabilistic and covers none of the newly-reachable
cases, so deterministic tests are added for restart seeding, an explicitly lower
caller-supplied ID, and two concurrent writers committing in reverse mint order. And
the executor records the **observed** RED failure count out of 50 in the SUMMARY rather
than "failed at least once", so a future reader can tell "fails about half the time as
predicted" from "fails for an unrelated reason".

## Revised 2026-08-01 after cross-AI review round 4 (`01-REVIEWS.md` H1, M1, M2, L2–L5)

**Round 4 is the first round in which neither reviewer rates this phase HIGH, and both
independently traced the in-transaction guard against real source and confirmed it
correct** — placement at all four append paths inside `sqlitex.ImmediateTransaction`,
in-transaction visibility of a batch's own earlier inserts, `EventID`-as-advisory with
no production read-back consumer, `RollbackToSnapshot` passing through the guard, and
the indexed-`MAX` cost on bulk paths being acceptable. **None of that is changed here.**
What follows are six local corrections.

**H1 — the one correctness defect: a zero ULID could collide with the empty-store
sentinel.** The round-3 revision gated the guard on *"when the log is non-empty"*. That
gating is the bug. On an empty store the comparison was skipped entirely, so a
caller-supplied zero ULID would insert verbatim; `MAX(event_id)` would then equal the
zero ULID, which is indistinguishable from `storage.ZeroChangeID`. `LatestEventID`
would report "empty" for a log holding one real event, and the sentinel would go out on
the wire for a non-empty store — the change ID silently meaning the opposite of the
truth. **The gating is removed in Task 3: the comparison now always runs, treating an
empty log as a zero maximum.** No production path mints a zero `EventID`, but
`EventStore.AppendEvent(s)` accepts caller-constructed envelopes
(`internal/storage/storage.go:51`) and a zero-value `domain.EventEnvelope` carries a
zero `EventID`, so the compliance suite is exactly where a future backend meets this.

**M1 — the "single INSERT funnel" claim was factually false, and this plan now says so.**
`internal/storage/sqlite/legacy_migration.go:183` executes a direct
`INSERT INTO events` carrying preserved Rust-era `e.eventID` values and bypasses
`insertEvent` entirely. Verified: `rg -n 'INSERT INTO events' internal/storage/sqlite/`
returns `eventstore.go:320` **and** `legacy_migration.go:183` (plus two test files).
The behavior is safe today and Task 3 records why; the defect was the unqualified
claim, which is the same *class* as round-3 H2 — a plan asserting an invariant the
codebase does not satisfy. All six occurrences of the claim in this plan are reworded
to "the single funnel for all **post-migration** appends".

**M2 — the restart-seeding test was not independently discriminating.** The
`internal/eventid` floor is package-global, so another test in the same binary (or a
second `-count` iteration of this very test) can raise it before
`TestInitialize_SeedsGeneratorFromPersistedLog` runs, leaving the "fresh" generator not
fresh; and if the test reads the ID back from storage, the in-transaction guard repairs
an unseeded proposal and the test passes with `Initialize`'s seeding deleted. Task 1
therefore restructures `internal/eventid` around a `Generator` value with a package
singleton plus `SwapDefault`, and Task 3's test asserts `eventid.New()` **immediately
after `Initialize` and before any append**. That before-any-append assertion is the
load-bearing half.

**L2 — name the bulk paths.** T-1-54 acknowledged the per-row `MAX` cost generically;
it now names `AppendEventsBatch` as both the import path and the rollback path
(`internal/server/service.go:836`).

**L3 — `internal/server/metrics_test.go:627` is decided here, not left to the
executor's compiler.** It is **exempt**, for two independent reasons stated in Task 3.

**L4 — compaction is safe because of seed + floor + guard together, not the guard
alone.** `CompactAggregate` deletes the aggregate *before* calling `insertEvent`
(`eventstore.go:252`, `:268-273`), so if the deleted aggregate held the global maximum,
the in-transaction `MAX` sees only the remaining log. The `internal/eventid` floor —
already raised past that deleted maximum — is what covers the difference. Tasks 1 and 3
require that combined-mechanism explanation to survive in the code comments and the
test rationale.

**L5 — record a bulk-path measurement.** Task 3 adds a focused `AppendEventsBatch`
benchmark at 1 / 100 / 1,000 / 10,000 events. **Recorded in the SUMMARY, deliberately
not a CI threshold** — this is an informational measurement, not a correctness gate,
and a threshold on a timing-sensitive benchmark would produce flaky failures that teach
a future maintainer to ignore it.

1. Create `internal/eventid/eventid.go`, package `eventid`, with a package doc
comment recording what the package exists for: every `EventEnvelope.EventID` in this
system is a ULID, and `MAX(event_id)` is used as the server's change ID (TMPL-08,
D-18), so an ID that sorts below an ID already in the log would make the change ID
fail to advance across a real state change — and a deduping consumer would then keep
serving a stale zone with no error anywhere.

State the division of responsibility plainly in that doc comment, because it is the
thing a later reader will get wrong: **this package makes minting monotonic; it does
not make commits ordered.** The ordering guarantee the change ID depends on is
enforced in the append transaction (`internal/storage/sqlite`), and this package is
what that guard mints through. Do not write a comment claiming that using this
package makes every append monotonic — it does not, and the previous revision of this
plan asserted exactly that and was wrong.

**Structure the state as a value type with a package singleton, not as bare package
variables** (review round-4 M2). A bare package-level floor can only ever be raised, so
no test can put it in a known starting state, and a same-binary test that raises it
first silently disarms the restart-seeding regression test Task 3 depends on.

Declare `type Generator struct` holding, under one `sync.Mutex`: an entropy source
built from `ulid.Monotonic(rand.Reader, 0)` (`crypto/rand`), matching what
`CommandHandler` builds today at `internal/server/commands.go:32` and `:43`, and a
`floor ulid.ULID` holding the greatest value this generator has issued or been seeded
with. The `inc` argument 0 is meaningful: in the pinned
`github.com/oklog/ulid/v2 v2.1.2` it defaults the increment ceiling to
`math.MaxUint32`, which is what makes successive IDs inside one millisecond strictly
increasing rather than random. Record that in a comment.

Give `Generator` three methods, and add a `func NewGenerator() *Generator` constructor
that returns one with a zero floor:

- `func (g *Generator) New() ulid.ULID` — under the lock, mint
  `ulid.MustNew(ulid.Timestamp(time.Now()), <entropy>)`; if the result does not
  compare strictly greater than `g.floor`, replace it with `next(g.floor)`; store the
  result as the new floor and return it. The floor comparison is what makes a
  backwards wall-clock step and a same-millisecond restart harmless rather than
  merely rare.
- `func (g *Generator) Seed(u ulid.ULID)` — under the lock, raise the floor to `u` when
  `u` compares greater than the current floor, and otherwise do nothing. Document that
  it is monotonic and idempotent so a caller cannot lower the floor, and that its
  purpose is to make the process generator monotonic against a **persisted** log at
  startup.
- `func (g *Generator) NewAfter(lower ulid.ULID) ulid.ULID` — `Seed(lower)` then
  `New()`, documented as the entry point for the in-transaction re-mint in Task 3 and
  guaranteed to return a value strictly greater than `lower`.

Then expose the package-level API every caller actually uses. Declare
`var defaultGenerator = NewGenerator()` guarded by a separate `sync.RWMutex` (name it
`defaultMu`), and declare `func New() ulid.ULID`, `func Seed(u ulid.ULID)` and
`func NewAfter(lower ulid.ULID) ulid.ULID` that take `defaultMu.RLock()`, read
`defaultGenerator`, release, and delegate to the corresponding method. These three are
the production entry points; nothing outside this package touches a `*Generator`
directly except a test.

Add `func SwapDefault(g *Generator) (restore func())` — under `defaultMu.Lock()`,
install `g` as the singleton and return a closure that reinstalls the previous one.
Document it as existing for exactly one purpose: a test that must observe a generator
whose floor it controls, because the floor is monotonic by design and therefore cannot
be lowered. State in that doc comment that production code never calls it, and that a
test which calls it must not use `t.Parallel()` because it mutates process-wide state.
Do not import `testing` from this file.

Add an unexported `func next(u ulid.ULID) ulid.ULID` returning the smallest ULID
strictly greater than `u`: copy `u`, increment the 80-bit entropy portion (bytes 6
through 15, big-endian) with carry; if it wraps to all zeros, increment the 48-bit
timestamp portion (bytes 0 through 5) with carry and leave the entropy at zero.
Document that carrying into the timestamp can produce an ID whose embedded
millisecond is a hair in the future, which is correct and preferable to a tie — the
timestamp is an ordering key here, not a claim about wall-clock time.

Prefer the library's own concurrency wrapper for the reader: run
`go doc github.com/oklog/ulid/v2 LockedMonotonicReader` first, and if that type exists
