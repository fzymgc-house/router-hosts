# Phase 1 Plan 09 — Change-ID Storage Foundation: Monotonic Event IDs and `LatestEventID`

<objective>
Establish the storage-layer premise TMPL-08 rests on, before any plan derives a change
ID from it: one monotonic event-ID generator that every append path uses, and a
`LatestEventID` read that returns the log's high-water mark.

Purpose: `MAX(event_id)` is a valid change ID **only** if no append can insert an ID
that sorts below an ID already in the log. That is currently false.
Output: `internal/eventid`, `storage.EventStore.LatestEventID`, `storage.ZeroChangeID`,
and a compaction regression test.

**Created 2026-08-01 in response to cross-AI review round 2** (`01-REVIEWS.md` H2).
Codex checked the claim the round-1 revision made and found it false in the repo
today: `internal/storage/sqlite/eventstore.go:258` mints the `HostCompacted`
replacement seed with a bare `ulid.Make()` inside `CompactAggregate`, bypassing
`CommandHandler.newID` (`internal/server/commands.go:60`) and the shared
`*ulid.MonotonicEntropy` entirely. Verified independently: `rg 'ulid\.(Make|New|MustNew)'`
over non-test Go files shows exactly two event-ID construction sites —
`commands.go:60` (monotonic) and `eventstore.go:258` (bare); `service.go:704` is a
snapshot ID and never enters `MAX(event_id)`.

The consequence is precisely the failure D-20 exists to prevent. A same-millisecond
bare ULID can sort **below** the maximum it replaces, so a compaction can leave
`MAX(event_id)` pinned or move it backward — the change ID fails to advance across a
real state change and a deduping consumer silently keeps serving a stale zone. D-22
anticipated compaction moving the ID *forward* and accepted one redundant render; it
did not anticipate it moving *backward*.

Plan 01 previously asked the executor to write a doc comment warning that "any future
change to ID generation must preserve monotonicity". The counterexample already
exists. REVIEWS.md calls this "a **prerequisite**, not a polish item: it invalidates
the premise TMPL-08 rests on." This plan is that prerequisite, and it runs in wave 1
before the tracer.

**Route-through-a-shared-generator was chosen over the alternative.** REVIEWS.md offered
two remedies: route compaction through a shared monotonic generator, or abandon lexical
`MAX(event_id)` for a database-owned sequence. The second means a schema migration, a
new monotonic column, and a rewrite of the change-ID premise in CONTEXT D-18 — a much
larger change that would invalidate the discussed design rather than repair it. The
first is a small, verifiable fix that makes D-18's stated mechanism actually true.
</objective>
