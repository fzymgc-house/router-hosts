# Phase 1 Plan 07 — Client Sink CLI — watch, Status File, Reconnect

<objective>
Turn the one-shot `render` path into a sink: a long-lived local process that keeps a
consumer's artifact current, survives connection loss, reloads the consumer's
resolver, and reports its own health both upstream and to a local file.

Purpose: the 0.10.12 failure mode #364 was filed over is a silently stale but
structurally valid zone. D-12 makes staleness visible through the marker and metrics
and never through a truncated or removed artifact — this plan is where that promise
is kept.
Output: `router-hosts watch`, the sidecar status file, and the post-write exec hook.
</objective>

  <behavior>
- Starting the command with a valid template and out path writes the artifact once, immediately, from the first snapshot.
- Adding a host causes the artifact to be rewritten with the new entry, with no polling and no operator action.
- Entries arriving before the snapshot terminator are buffered and not rendered; the artifact is written exactly once per completed snapshot.
- A snapshot whose entry count exceeds the client collection limit is refused and the previous artifact stays byte-identical.
- A snapshot whose contract version differs from the template's declared version is refused and the previous artifact stays byte-identical.
- A render error leaves the previous artifact byte-identical and increments the sidecar's consecutive-failure count.
- A successful write updates the sidecar with a new last-success time and a zero failure count, then runs the post-write command when one is configured.
- The command sends a status message upstream on its own interval, independent of whether host data changed.
- SIGINT or SIGTERM ends the command cleanly without writing a partial artifact.
  </behavior>
  <action>
1. `internal/client/commands/watch.go` — `func newWatchCmd() *cobra.Command` with
`Use: "watch"`, a required `--template` flag, a required `--out` flag, and
optional `--exec`, `--status-file`, `--status-interval` (default 30s) and
`--exec-timeout` (default `defaultPostWriteHookTimeout`) flags. Register it in
`NewRootCmd` next to the `render` command.

`RunE` must not reuse the fixed 30 second one-shot deadline helper defined in
`host.go` — that deadline would tear down the stream. Derive the lifetime context with
`signal.NotifyContext(cmd.Context(), syscall.SIGINT, syscall.SIGTERM)` and defer
the stop function. Parse and version-declare the template before connecting, the
same way `render` does.

2. Implement `func runWatch(ctx context.Context, ...) error` holding one stream
session: open `c.Hosts.WatchHosts(ctx)`, send an opening request with follow set
true, then run two concurrent roles exactly as the server does — a ticker
goroutine that is the sole owner of `stream.Send` and emits a `SinkStatus`
carrying the current last-success Unix seconds, consecutive-failure count and
declared contract version every `--status-interval`; and the calling goroutine as
the sole owner of `stream.Recv`. Never call `Send` from the receive loop.

3. The receive loop accumulates entries from the entry arm into a buffer, applying
the plan 03 collection cap before each append and refusing the whole snapshot
rather than truncating. When the terminator arm arrives: call
`template.RequireVersion(declared, served)`; call `template.FromProto` and
`template.Render` into memory; call `atomicfile.Write(outPath, rendered)`; then
write the sidecar status and run the post-write hook. Reset the entry buffer to
empty after every terminator, and on every error path, so a partial snapshot can
never be carried into the next render — that reset is what makes an interrupted
stream unable to produce a truncated artifact.

4. Failure handling is uniform and non-fatal to the process: a cap refusal, a
version mismatch, a render error, a write error, or a post-write hook error all
log at error level with `slog`, increment the consecutive-failure count, write
the sidecar with the error text, and leave the artifact untouched. Only a stream
error or a context cancellation ends `runWatch`, and it returns that error to the
caller (Task 3 turns a stream error into a reconnect). Under no circumstance may
the command delete, truncate, or partially write the artifact — staleness is
surfaced through the marker and the metrics, never through the artifact itself.

5. `internal/client/commands/watch_test.go` — build on `setupCmdTest(t)` and run
the command in a goroutine with a cancellable context and bounded waits. Add
`TestWatch_WritesInitialArtifact`, `TestWatch_RewritesOnMutation`,
`TestWatch_PartialSnapshotNotRendered`, `TestWatch_CapExceededPreservesArtifact`,
`TestWatch_VersionMismatchPreservesArtifact`,
`TestWatch_RenderErrorPreservesArtifactAndRecordsFailure`,

`t.TempDir()`), and `TestWatch_ContextCancelStopsCleanly`. Every test must use
`t.TempDir()` and a bounded wait; none may block indefinitely.

  <name>Task 3: Self-healing reconnect with bounded backoff</name>
  <files>internal/client/commands/watch.go, internal/client/commands/watch_test.go</files>
  <read_first>
- internal/client/commands/watch.go (Task 2's `runWatch` — the single-session function this task wraps)

  </read_first>
  <behavior>
- When the stream ends with an error, the command waits a backoff interval and opens a new stream rather than exiting.
- Successive failures increase the wait, up to a bounded maximum.
- A successful reconnect resets the backoff to its initial value.
- A reconnect produces a complete fresh snapshot and a full artifact rewrite — no resume token or delta is sent.
- The artifact is byte-identical across a disconnect that is followed by no data change.
- Connection loss increments the sidecar's consecutive-failure count and records the error text without clearing the last-success time.
- Cancelling the context during a backoff wait ends the command promptly rather than sleeping out the interval.
  </behavior>
  <action>
Wrap `runWatch` in a supervising loop inside the command's `RunE`.

Declare `watchInitialBackoff = 1 * time.Second` and `watchMaxBackoff = 60 * time.Second`
with doc comments. The loop: call `runWatch`; if the context is done, return nil;
otherwise record the failure to the sidecar (incrementing the consecutive-failure
count, preserving the last-success time), log at warn level with `slog`, then wait
for the current backoff using a `select` over `ctx.Done()` and a `time.After`
timer so cancellation is immediate. Double the backoff on each consecutive
failure, clamped at `watchMaxBackoff`, and reset it to `watchInitialBackoff` as
soon as a session successfully completes a snapshot write.

Apply jitter to the wait — multiply by a random factor in the range 0.5 to 1.5
using `math/rand` — so N sinks that lost a server at the same instant do not
reconnect in lockstep. Do not use `crypto/rand`; this is scheduling jitter, not a
security decision, and a linter may otherwise flag the choice, in which case
document the reason rather than suppressing the warning.

A reconnect sends nothing but a fresh follow request: the server keeps no
per-stream position by design (D-06/D-08), so the next snapshot is the complete
current state. Add a comment recording that, because a future reader will be
tempted to add a resume token.

<threat_model>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| server stream to local artifact file | Server-supplied data becomes a file a resolver daemon parses and acts on |
| `--exec` command string to the local shell | An operator-supplied string is executed by `sh -c` with the sink process's privileges |
| `--out` and `--status-file` paths to the filesystem | Two operator-supplied paths are written on every successful cycle |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-1-24 | Elevation of Privilege | the `--exec` post-write hook as an arbitrary-command-execution surface | high | mitigate | The command is supplied by the operator who launched the sink and runs with exactly that process's privileges — it grants no capability the launcher did not already have. It is bounded by a context timeout (default 30s, `--exec-timeout`), never receives server-supplied data as arguments (it is invoked as a fixed string, with no interpolation of entry fields), and its failure is recorded rather than escalated. This is the same trust model and the same `sh -c` shape as the already-reviewed server-side hooks at `internal/server/hooks.go:197`. |
| T-1-25 | Tampering | a truncated or partial artifact observed by a resolver mid-reload | high | mitigate | Two independent guards: entries are buffered until the snapshot terminator so a partial snapshot is never rendered, and the render completes into memory before `atomicfile.Write` does its temp-plus-rename. Asserted by `TestWatch_PartialSnapshotNotRendered` and `TestWatch_ReconnectNoTruncation`. |
| T-1-26 | Denial of Service | a malicious server driving the sink out of memory across snapshots | high | mitigate | Plan 03's configurable entry cap is applied before every append, and the entry buffer is reset at every snapshot boundary and on every error path, so accumulation cannot compound across snapshots. |
| T-1-27 | Tampering | symlink or traversal attack on `--out` or `--status-file` | medium | mitigate | Both paths go through `atomicfile.Write`, whose temp-plus-rename replaces a symlink at the destination rather than following it. Both paths are operator-supplied and the process runs with the operator's own privileges, so no further confinement is added; the behavior is documented in `docs/reference/template-contract.md`. |
| T-1-28 | Denial of Service | N sinks reconnecting in lockstep after a server restart | medium | mitigate | Exponential backoff from 1s to 60s with a 0.5-to-1.5 random jitter factor, so a fleet spreads its reconnect attempts. |
| T-1-29 | Repudiation | a silently stale artifact indistinguishable from a current one | high | mitigate | The sidecar status file records last success, last error and consecutive failures on every cycle, and is the only health signal available when the server itself is down (D-11). Server-side last-seen metrics cover the complementary case. |
| T-1-SC | Tampering | npm/pip/cargo installs | high | mitigate | Not applicable: no new external packages and no package-manager install task exists in this plan. |

</threat_model>
