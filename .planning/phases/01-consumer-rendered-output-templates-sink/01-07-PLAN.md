# Phase 1 Plan 07 — Client Sink CLI — watch, Status File, Reconnect

<objective>
Turn the one-shot `render` path into a sink: a long-lived local process that keeps a
consumer's artifact current, survives connection loss, reloads the consumer's
resolver, and reports its own health both upstream and to a local file.

Purpose: the 0.10.12 failure mode #364 was filed over is a silently stale but
structurally valid zone. D-12 makes staleness visible through the marker and metrics
and never through a truncated or removed artifact — this plan is where that promise
is kept.
Output: `router-hosts watch`, the sidecar status file, and the post-write exec hook.

**Revised 2026-07-31 after cross-AI review** (`01-REVIEWS.md`).

**H3 — the pre-review plan's failure guarantee was impossible.** It said hook errors
follow the same path as render and write errors and leave the artifact untouched.
They cannot: by the time the hook runs, the artifact has already been replaced.
CONTEXT D-12a resolves this into **three** distinct outcomes, and the middle one is
the operationally important one — "your zone file is correct but your resolver did
not pick it up" is a different page from "your zone file is old". The artifact is
**never rolled back after the hook has run**, because on hook failure it is unknown
whether the resolver already read the new file, so reverting could leave the on-disk
file and the running resolver actively disagreeing. This plan therefore needs a
reload-health field, not a reinterpretation of the existing error field.

**H4 — the status ticker read last-success and failure state while the receive loop
wrote it, with no ownership model stated.** The suite runs under `-race`, so that is
a build-breaking gap, not a theoretical one. Ownership is now explicit: one
mutex-guarded type owns the state and serves immutable snapshots, matching the
locking discipline `hookrunner.go` already uses in this repo.

**TMPL-08** adds the client half of change identity: record the change ID that was
rendered, report it upstream, and skip a redundant render when it repeats — the
permitted half of D-21.
</objective>

2. **Define the ownership model before any concurrent code exists** (review H4).

`type sinkHealthState struct { mu sync.Mutex; st sinkStatus }` with:

- `func (s *sinkHealthState) recordSuccess(changeID string, at time.Time)` —
  sets `last_success` and `rendered_change_id`, clears `last_error`, zeroes

2. Implement `func runWatch(ctx context.Context, ...) error` holding one stream
session: open `c.Hosts.WatchHosts(ctx)`, send an opening request with follow set
true **and the current health snapshot attached as its status payload** — the
server records a status on the opening message (plan 06), and on a reconnect that
is how a sink immediately reports the change ID it already has on disk. Then run
two concurrent roles exactly as the server does: a ticker goroutine that is the
sole owner of `stream.Send` and emits a `SinkStatus` every `--status-interval`,
and the calling goroutine as the sole owner of `stream.Recv`. Never call `Send`
from the receive loop.

The ticker builds its message **only** from `health.snapshot()` — the
mutex-guarded owner from Task 1. It must not read any field the receive loop
writes, and it must not hold a pointer into the state. That single rule is the
whole ownership model; review H4 flagged this pairing as an unspecified race, and
the suite runs under `-race`, so an ad-hoc shared field will fail the build rather
than merely being untidy. The message carries last-success Unix seconds,
consecutive-failure count, declared contract version, rendered change ID,
reload-failed flag and last-reload-success Unix seconds.

3. The receive loop accumulates entries from the entry arm into a buffer, applying
the plan 03 entry cap and byte budget before each append and refusing the whole
snapshot rather than truncating. When the terminator arm arrives, run the cycle in
this exact order:

   a. `template.RequireVersion(declared, served)`.
   b. **Change-ID skip (D-21 client half, TMPL-08).** If the terminator's change
   ID is non-empty and equals the last rendered change ID **and** the artifact
   path still exists (`os.Stat` succeeds), skip the render, the write and the
   hook, log at debug level, and reset the buffer. Both conditions are
   required: guarding on the ID alone would make an out-of-band deletion
   permanent, because no future snapshot would ever rewrite the file. This skip
   is what stops a server restart from triggering a simultaneous reload storm
   across every sink in the fleet, which is the operationally valuable half of
   change identity. Note at this site that the mirror-image optimization on the
   server is forbidden by D-21 — a server-side skip needs per-consumer position
   tracking, which is the resume token D-06 and D-08 reject.
   c. `template.FromProto` and `template.Render` into memory.
   d. `atomicfile.Write(outPath, rendered)`.
   e. `health.recordSuccess(changeID, now)` — the artifact is now current, and
   this is true regardless of what the hook does next.
   f. `runPostWriteHook(...)` when one is configured. On success,
   `health.recordReloadSuccess(now)`. On failure,
   `health.recordReloadFailure(err, now)` and log at error level.
   g. Write the sidecar from `health.snapshot()`.

   Reset the entry buffer to empty after every terminator, and on every error
   path, so a partial snapshot can never be carried into the next render — that
   reset is what makes an interrupted stream unable to produce a truncated
   artifact.

4. **Failure handling is not uniform, and the pre-review plan was wrong to say it
was.** A sink cycle has three outcomes (D-12a), and steps (b) through (g) above
are ordered so the code cannot conflate them:

   - **Render or write failure** (steps a-d): the artifact was never replaced, so
     the previous one is still on disk byte-identical. Call
     `health.recordFailure(err)`, log at error level, write the sidecar.
   - **Artifact written, hook failed** (step f): the artifact **is updated and
     retained**. Do not delete it, do not restore the previous content, do not
     re-render. `recordSuccess` has already run and must not be undone —
     `recordReloadFailure` sets reload health alongside it. Rolling back here is
     forbidden: it is unknown whether the resolver already read the new file, so a
     revert can leave the file and the running resolver actively disagreeing.
   - **Connection loss**: the artifact is unchanged and stale. Handled by Task 3's
     supervising loop, which calls `health.recordFailure` before backing off.

   A cap refusal and a version mismatch are render-path failures — first row. Only
   a stream error or a context cancellation ends `runWatch`, and it returns that
   error to the caller. Under no circumstance may the command delete, truncate, or
   partially write the artifact — staleness is surfaced through the marker and the
   metrics, never through the artifact itself.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| server stream to local artifact file | Server-supplied data becomes a file a resolver daemon parses and acts on |
| `--exec` command string to the local shell | An operator-supplied string is executed by `sh -c` with the sink process's privileges |
| `--out` and `--status-file` paths to the filesystem | Two operator-supplied paths are written on every successful cycle |

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |

| T-1-24 | Elevation of Privilege | the `--exec` post-write hook as an arbitrary-command-execution surface | high | mitigate | The command is supplied by the operator who launched the sink and runs with exactly that process's privileges — it grants no capability the launcher did not already have.
