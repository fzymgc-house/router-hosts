# Phase 1 Plan 11 — Real-process cold-start e2e for the `--config` seam (gap G-01-1)

<objective>
Close gap G-01-1's coverage half: build a real-process cold-start e2e suite that launches
the shipped binary as an OS process and proves `watch --config <path>` targets the server
named in `<path>`.

Purpose: this is not a redundant second test of plan 01-10. The entire existing `e2e`
suite builds its server object directly and drives the client through the root command
inside the SAME process; `docker_e2e` puts the server in a container but still drives the
client in-process. Neither crosses an OS process boundary on the client side, so the
CLI-flag-to-config-loading seam is never exercised by anything. That structural blind spot
is exactly why G-01-1 shipped green through a full phase with 45 UAT items and a passing
verification report.

The corollary this suite exists to fix: **"e2e passes" in this repo has not meant "the
shipped binary works when launched from a shell."** An in-process test for this bug would
faithfully reproduce the blind spot that hid it.

This plan runs in wave 2 because its whole point is to OBSERVE plan 01-10's fix from
outside. Task 1 is the tracer: one thin path through build, PKI, config files, two live
server processes, one live sink process, and an on-disk artifact assertion.

Output: build tag `proc_e2e`, a reusable process harness, three tests, a `task` target,
and a recorded design for the deferred container harness this must not foreclose.
</objective>

<build_tag_decision>

## Build tag decision

**Chosen: a new `proc_e2e` build tag and a new `task test:e2e:proc` target, not an
overload of the existing `e2e` tag.** Rationale, stated deliberately because the
constraint asked for a considered choice:

- `task test:e2e` currently runs the `e2e` tag with no build dependency, so every test
  under it runs from source. Overloading `e2e` would silently make that target require
  `bin/router-hosts` to exist and be current, turning a stale binary into a confusing
  failure in an unrelated suite — or worse, into a pass against a binary built before the
  fix.
- `e2e/helpers_test.go` carries the `e2e || docker_e2e` tag and imports the server and
  storage packages to build servers in-process. Adding a third tag to that file would pull
  all of it into a suite whose defining property is that it constructs nothing in-process.
  The new harness is therefore standalone, duplicating roughly ninety lines of certificate
  generation rather than importing its way into the in-process world. That duplication is
  the cheaper of the two costs, and it is called out here so a future reader does not
  "fix" it by merging the files.
- Three tiers, three tags, three targets, each stating what it does and does not prove:
  `e2e` (in-process, real TLS), `docker_e2e` (containerized server, in-process client),
  `proc_e2e` (real processes on both sides).

**Deliberate non-goal: this target is NOT added to CI.** `.github/workflows/ci-go.yml`
does not run `task test:e2e` or `task test:e2e:docker` either. Wiring only the new suite
into CI would be an unrequested change to the repo's existing testing posture, made
sideways inside a gap-closure plan. Task 3 records this as a known limitation with a filed
follow-up issue rather than silently deciding it either way.

</build_tag_decision>

## Forward compatibility with the deferred container harness

UAT test 42 is blocked pending a real unbound host and a second machine, and its Deferred
Follow-Up ties itself to this work: *"both want a process/container-level harness rather
than the current fully in-process e2e suite; worth designing as one harness, not two."*

Building that containerized unbound and two-node convergence verification is **out of
scope here and stays deferred.** What IS in scope is not building a single-purpose harness
that would have to be thrown away when it arrives.

The structural commitment, which Task 1 must implement and Task 3 must record:

1. **PKI is N-party from the start.** Client certificates are minted by a function taking
   a CN parameter, not a hard-coded one. Sink health is keyed by mTLS CN, so a two-node
   convergence test needs two distinct CNs; a harness that mints one is unextendable.
2. **Config generation is transport-agnostic.** The server and client config writers emit
   TOML files to a directory and take an address as a parameter. A container harness mounts
   the same directory and passes a container-network address; nothing about the writers
   assumes loopback or a particular launch mechanism.
3. **Launch is the only container-specific seam.** Process start and stop is confined to
   small launcher functions. Swapping them for container invocations replaces those
   functions and nothing else.
4. **Observation is filesystem-based, not in-memory.** Artifact and sidecar assertions read
   files by path with a polling deadline. A bind-mounted container volume satisfies the
   identical assertion unchanged.
5. **Multiple sinks are already expressible.** The sink launcher returns a handle with its
   own artifact and sidecar paths, so starting two sinks against one server is a second
   call, not a refactor.

Deliberately left out, to be recorded in Task 3: no docker-compose file, no unbound
container, no cross-container networking, no resolver-reload assertion, and no two-node
convergence test. Those belong to test 42, not to this plan.

</forward_compat_mandate>

Harness (`e2e/proc_harness_test.go`), with these named symbols:

- `procBinaryPath(t)` — resolves the binary from `ROUTER_HOSTS_BIN`, defaulting to
  `../bin/router-hosts` relative to the package directory. If it is absent, call
  `t.Fatalf` naming the binary path and telling the reader to run `task build`. Use
  `t.Fatalf`, never `t.Skip`: a suite that skips itself when its subject is missing is a
  green report that tested nothing, which is the same class of failure as the gap being
  closed.
- `pkiBundle` and `newPKIBundle(t, dir)` — generates a CA and a server leaf (`localhost`
  DNS SAN plus 127.0.0.1 and ::1 IP SANs, server-auth EKU) and writes them to `dir`.
  Adapted from the helpers named in the read-first list.
- `issueClientCert(t, b, cn)` — mints a client-auth leaf with the caller's CN and writes
  cert and key, returning both paths. The CN must be a parameter, per the forward-compat
  mandate: sink health is keyed by CN and a future two-node test needs two.
- `reserveLocalPort(t)` — binds loopback on port 0, records the chosen port, closes the
  listener, returns the port. Document the accepted time-of-check window in a comment: the
  port could in principle be taken between close and the server's bind, which is why the
  readiness poller below has a real deadline and a real failure message rather than an
  infinite wait.
- `writeServerConfigFile(t, dir, addr, b)` and
  `writeClientConfigFile(t, path, addr, caPath, certPath, keyPath)` — emit TOML to disk.
  Both take the address as a parameter and assume nothing about loopback, so a container
  harness can reuse them verbatim.
- `startServerProcess(t, bin, cfgPath, addr, b)` — launches the `serve` subcommand with
  its config flag using a context-bound command, captures stdout and stderr into buffers,
  polls until a TLS dial to `addr` succeeds with a deadline around ten seconds, and
  registers a `t.Cleanup` that signals termination, waits briefly, force-kills if needed,
  and dumps the captured output when the test has failed. Returns a handle carrying the
  address and a stop function so a test can take a server down mid-run.
- `startSinkProcess(t, bin, clientCfgPath, tmplPath, outPath, env)` — launches the `watch`
  subcommand with its config, template, and out flags the same way, returns a handle
  carrying `outPath` and its sidecar path (`outPath` with `.status` appended), and cleans
  up the same way. Multiple concurrent calls must be safe: each handle owns its own paths.
- `runCLI(t, bin, env, args...)` — runs a one-shot subcommand to completion and returns
  combined output plus the exit error, for `host add` and for the negative test.
- `hermeticEnv(t, xdgDir)` — builds the explicit child-process environment. This is
  load-bearing and must not be skipped: set `XDG_CONFIG_HOME` to the caller's directory,
  set `HOME` to a fresh temp directory so the `~/.config` and darwin
  `~/Library/Application Support` fallbacks cannot reach a developer's real config, and
  set each `ROUTER_HOSTS_*` variable named in the client config source to the empty
  string. Pass this explicitly as the child's environment rather than inheriting the
  parent's. A test that accidentally inherits the developer's config would pass on that
  developer's machine for the wrong reason.
- `waitForFileContent(t, path, deadline, predicate)` and
  `waitForSidecar(t, path, deadline, predicate)` — poll a path until it exists and its
  parsed content satisfies the predicate, failing with the last observed content when the
  deadline passes. Sidecar parsing uses `encoding/json` against the field names in the
  read-first list; declare a local `procSinkStatus` struct in the test package rather than
  reaching into the unexported client type.
