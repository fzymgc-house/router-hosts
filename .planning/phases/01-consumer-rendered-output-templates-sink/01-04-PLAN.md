# Phase 1 Plan 04 — Lazy Wire Streaming and gRPC Keepalive

<objective>
Deliver TMPL-06 as amended: bound per-message wire memory and give the client real
backpressure, on both the new `WatchHosts` stream and the existing `ExportHosts`
stream, without changing a single output byte of the three fixed export formats.
Then configure gRPC keepalive on both sides, because the sink health metrics
D-09/D-10 add later are meaningless if a dead connection can sit undetected for the
grpc-go default of two hours.

Purpose: 01-RESEARCH.md found no keepalive configured anywhere in this repo, and
found that `ExportHosts` builds one blob and sends it in a single message.
Output: chunked `ExportHosts` sends, a per-entry streaming assertion for
`WatchHosts`, explicit keepalive parameters on server and client, and an operations
guide section.

**Revised 2026-07-31 after cross-AI review** (`01-REVIEWS.md` H2). The two reviewers
split on TMPL-06: pi rated the plan's honesty a strength, Codex rated the
requirements gap HIGH — "calling the limitation 'honest' does not make the
requirement satisfied". Both were right about different things, and the resolution
was a decision rather than a plan edit: **TMPL-06 and roadmap criterion 5 were
amended** to require bounded wire messages and client backpressure, with
storage-layer laziness explicitly deferred to **#400**. This plan now satisfies its
requirement rather than documenting a shortfall against it. The `known_limitations`
entry cites the amended requirement and the follow-up issue instead of describing an
unmet obligation, and no artifact this plan writes claims constant server memory.
This plan also picks up round-1 review L2: the pre-existing `ExportHosts` tests read
only the first response (`service_test.go:492`, `:514`, `:552`), so they pass on small
payloads without establishing byte identity after chunking — three new all-format
reconstruction tests do that.

**Revised 2026-08-01 after cross-AI review round 2** (`01-REVIEWS.md` L14, L12). Two
additions, both small.

**L14 — the empty payload is a deliberately preserved special case with no test.** The
plan explicitly says "when `data` is empty, send exactly one message carrying an empty
chunk so the existing single-message expectation for an empty inventory still holds",
and then never asserts it. A chunking loop written the obvious way (`for len(data) > 0`)
sends *zero* messages for an empty payload, which is a different observable contract
and would break the client's drain. Task 1 now pins it, together with the exact
boundary either side of one chunk.

**L12 — the keepalive change is fleet-wide, not sink-specific.** `NewClient` is the
constructor every CLI command uses, so 20-second pings with `PermitWithoutStream`
apply to a one-shot `host list` and to a long-lived `watch` alike. That is the right
default and the plan keeps it, but an operator on a constrained or metered link needs
to know it happened and what it costs. The operations guide now says so explicitly
rather than describing it as sink behavior.
</objective>

1. `internal/server/service.go` — add an unexported constant
`exportChunkSize = 64 * 1024` next to the existing export code, with a doc

`return stream.Send(&hostsv1.ExportHostsResponse{Chunk: data})` with a loop that

identity either: each reads only the first response

payload whether or not chunking reassembles correctly (review L2).

Add three reconstruction tests, one per format, each seeding enough entries that
the formatted payload exceeds `exportChunkSize`, draining the whole stream,
asserting the message count is greater than one, and asserting the concatenation
of every chunk equals the expected payload byte for byte:
`TestService_ExportHosts_ChunksLargePayloadHosts` against
`(&HostsFileGenerator{}).FormatHostsFile(entries)`,
`TestService_ExportHosts_ChunksLargePayloadJSON` against the same JSON
construction the handler performs, and
`TestService_ExportHosts_ChunksLargePayloadCSV` against the same CSV
construction. Building the expectation from the handler's own helper rather than
from a hand-written string keeps the test honest about format while still proving
reassembly. Also assert in each that every chunk except possibly the last is
exactly `exportChunkSize` bytes, so a framing bug that emits ragged chunks is
caught rather than hidden by a correct concatenation.

Add three more cases in `service_test.go` covering the framing boundary and the
preserved empty-payload contract (review L14):
`TestService_ExportHosts_EmptyInventorySendsOneChunk` — export an empty store and

responses whose second chunk is one byte long. Build the padding from a comment field
so the payload length is controllable without touching the format code.

Also add `TestService_ExportHosts_RepeatedCallsAreIdentical`: two consecutive exports
