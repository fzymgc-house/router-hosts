# Phase 1 Plan 03 — Bounded, Fail-Loud Client Stream Collection

<objective>
Close TMPL-07: a malicious or buggy server can currently drive the CLI out of memory
because `collectHostStream`, `collectSearchStream` and `collectSnapshotStream` all
`append` without any ceiling, and the new `render` drain loop inherits the same
shape.

Purpose: D-15 makes this load-bearing rather than theoretical — because `.Count` and
`.GeneratedAt` are part of the contract, the client must hold the whole entry set
before rendering, so the cap is the only thing bounding it.
Output: a configurable, fail-loud collection limit applied at every collecting call
site, with safe defaults.

**Revised 2026-07-31 after cross-AI review** (`01-REVIEWS.md`). Review L1: an entry
count is not a byte bound. Hostnames are capped at 253 bytes and aliases at 50
(`internal/validation/validation.go:32`, `:82`), but comments and tags have no
equivalent limit, so a server can exhaust a client with far fewer than 50,000 very
fat entries. This plan therefore bounds both dimensions. Review L6: the per-test
small-limit seam was the only test-critical mechanism left open in the whole plan
set — it is now pinned to a named client option so it cannot be improvised
differently by each executor.

**Revised 2026-08-01 after cross-AI review round 2** (`01-REVIEWS.md` H3, M7, M8).

**H3 — the strict validation this plan adds would have been dead code.** Codex checked
`LoadClientConfig` and found it shadows and discards *both* inner errors
(`internal/config/client.go:55-59`): `findClientConfigFile` is called under
`if path, err := ...; err == nil`, and `loadClientConfigFile(path)` under a second
`if fileCfg, err := ...; err == nil`. Verified independently — the file-loading branch
accepts a result only on success and silently ignores every failure otherwise. So a
config file that exists but is malformed, carries an unknown key, or fails validation
falls back to defaults with no error anywhere, and the strict `meta.Undecoded()`
rejection at `:97` never reaches a caller. Adding `[limits]` fields on top of that
means their validation is unreachable through the file path too. REVIEWS.md is
explicit that fixing this after the limits ship leaves the new validation dead, so it
is **Task 1 here**, before the fields exist.

**M7 — `proto.Size` bounds serialized bytes, not retained heap.** Slice headers, string
headers and converted-object overhead sit outside it, so the doc comment and the
configuration reference must describe the byte budget as a conservative bound on
received wire volume, not an exact memory ceiling. It is still the right measurement —
it is exactly what crossed the wire — but the documentation must not promise 64 MiB of
heap.

**M8 — the test-helper signature change breaks every existing caller unless it is
explicitly variadic.** `setupCmdTest` currently takes only `t`
(`internal/client/commands/testhelper_test.go:23`), and the round-1 plan said to
"extend it to accept optional `client.Option` values" without pinning the shape. The
signature is now stated exactly.
</objective>
