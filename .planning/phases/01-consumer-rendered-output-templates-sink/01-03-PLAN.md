# Phase 1 Plan 03 — Bounded, Fail-Loud Client Stream Collection

<objective>
Close TMPL-07: a malicious or buggy server can currently drive the CLI out of memory
because `collectHostStream`, `collectSearchStream` and `collectSnapshotStream` all
`append` without any ceiling, and the new `render` drain loop inherits the same
shape.

Purpose: D-15 makes this load-bearing rather than theoretical — because `.Count` and
`.GeneratedAt` are part of the contract, the client must hold the whole entry set
before rendering, so the cap is the only thing bounding it.
Output: a configurable, fail-loud collection limit applied at every collecting call
site, with safe defaults.

**Revised 2026-07-31 after cross-AI review** (`01-REVIEWS.md`). Review L1: an entry
count is not a byte bound. Hostnames are capped at 253 bytes and aliases at 50
(`internal/validation/validation.go:32`, `:82`), but comments and tags have no
equivalent limit, so a server can exhaust a client with far fewer than 50,000 very
fat entries. This plan therefore bounds both dimensions. Review L6: the per-test
small-limit seam was the only test-critical mechanism left open in the whole plan
set — it is now pinned to a named client option so it cannot be improvised
differently by each executor.
</objective>

truncated, and the two ways to raise that specific bound — the
`limits.max_stream_entries` / `limits.max_stream_bytes` client-config key and the

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| server stream to client memory | Every response message the client accumulates is attacker-controllable in volume by a compromised or buggy server |
| environment and config file to limit value | The ceiling protecting client memory is itself operator-supplied input |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-1-05 | Denial of Service | unbounded `append` in `collectHostStream`, `collectSearchStream`, `collectSnapshotStream`, and the `render` drain loop | high | mitigate | Two independent per-call ceilings checked before each append: an entry count defaulting to 50,000 and a byte budget defaulting to 64 MiB measured with `proto.Size` on the received message. Crossing either returns a nil slice plus a named error. This upgrades plan 01's compiled-in floor to the configurable bound and closes review L1, which observed that hostnames and aliases are length-validated but comments and tags are not, so an entry count alone does not bound memory. |
| T-1-09 | Tampering | a limit value that disables the protection (zero, negative, or unparseable) | medium | mitigate | Zero resolves to the safe default rather than to "unlimited"; negative values and unparseable env values are rejected by `ClientConfig.validate` with a validation-coded `oops` error, so the process refuses to start rather than running unprotected. The same rule applies to both bounds. |
| T-1-10 | Denial of Service | silent truncation masking a real inventory that outgrew the limit | medium | mitigate | The refusal returns a nil slice and an error naming both the limit and the two ways to raise it (D-14 forbids silent truncation); tests assert the empty result explicitly. |
| T-1-SC | Tampering | npm/pip/cargo installs | high | mitigate | Not applicable: no package-manager install task exists in this plan and 01-RESEARCH.md's Package Legitimacy Audit records zero new external packages. |
