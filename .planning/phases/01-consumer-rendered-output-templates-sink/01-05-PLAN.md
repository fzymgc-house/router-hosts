# Phase 1 Plan 05 — Sink Health Primitives — Identity, Registry, Gauges

<objective>
Build the three server-side primitives sink health needs, as standalone, unit-tested
units with no RPC wiring: mTLS common-name extraction, an in-memory per-consumer
health registry, and the OTel observable gauges that project it.

Plan 06 wires these into the `WatchHosts` handler. Keeping them separate here means
the concurrency work in plan 06 lands against primitives that are already proven.

Purpose: D-09 puts sink health on the server's existing OTel pipeline instead of
standing up an OTel publisher at every consumer; D-10 keeps last-seen alive across a
closed stream so absence becomes a measurable age; D-13 bounds label cardinality by
verified identity.
Output: `commonNameFromContext`, `SinkHealth`, `(*Metrics).RegisterSinkGauges`.

**Revised 2026-07-31 after cross-AI review** (`01-REVIEWS.md`). Three changes.
**M5:** `router_hosts_sink_render_failures_total` was created here and incremented
nowhere — no plan supplied a protocol event or an invocation point, so it would ship
permanently zero. It is removed rather than wired: a client-reported failure *count*
is gauge-like state, and deriving counter increments from repeated status reports
double-counts every re-report. The existing `router_hosts_sink_consecutive_failures`
gauge already carries that state faithfully. **M6:** the "bounded by construction"
cardinality claim was too strong and is restated precisely below. **D-12a and
TMPL-08:** the registry gains reload health (separate from write health) and the
last rendered change ID, which is exposed as a bounded 0/1 convergence gauge rather
than as a label value.
</objective>

Methods:

- `RecordSeen(cn string)` sets `LastSeen` to `time.Now().UTC()`.
- `RecordStatus(cn string, st SinkState)` merges the reported fields and refreshes
  `LastSeen`. Take a struct rather than a widening parameter list — six positional
  arguments is where transposed-argument bugs live. Do **not** derive
  `LastSuccess` from `ReloadFailed` or vice versa; they are independent.
- `RecordServerChange(changeID string)` stores the server's current change ID. One
  string for the whole server, not one per consumer — the change ID identifies
  state, so every consumer is compared against the same value (D-19).
- `Connect()` and `Disconnect()` adjust the connected counter, clamped at zero.
  They take **no common name**: `router_hosts_sinks_connected` carries no labels,
  so the count needs no identity, and making it identity-free is what lets a
  stream with an unverifiable peer still be counted — and lets a test observe
  handler teardown deterministically without needing a verified chain.
  `Disconnect` deliberately leaves the state entry in place — that retention is
  D-10 and is what removes the clean-shutdown-versus-crash ambiguity.
- `Snapshot() SinkSnapshot` returning `type SinkSnapshot struct {
  States map[string]SinkState; Connected int64; ServerChangeID string }`, with the
  map a defensive copy. A named struct rather than a multi-value return, because
  the callback now needs three things and positional returns get transposed.

Declare `MaxTrackedSinks = 1000`. Its doc comment must state what the ceiling
actually bounds, and what it does not — review M6 found the original claim too
strong. It bounds the number of entries the registry holds, and therefore the

lifetime: an evicted CN that reconnects reappears, and the backend keeps both.

CA-issued mTLS common names (D-13), never from anything a caller supplies. Write
the comment in those terms rather than as "bounded by construction". When a write
would insert a name beyond the ceiling, evict the entry whose `LastSeen` is oldest
before inserting, and log the eviction at warn level with `slog` using structured
key-value pairs in the style of `service.go:130-168`.

All methods must be safe for concurrent use — this registry is written from N
concurrent stream goroutines and read from the OTel scrape callback.

## Trust Boundaries

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-1-15 | Spoofing | a consumer claiming another consumer's identity to poison its health metrics | high | mitigate | Identity is read only from `VerifiedChains[0][0].Subject.CommonName` on a connection the server already required and verified a CA-signed client certificate for (`internal/server/server.go:207`). No request-body field participates in identity, asserted by an acceptance criterion. |
| T-1-16 | Denial of Service | metric-storage exhaustion via unbounded label cardinality | high | mitigate | Claim restated after review M6, which found the original "bounded by construction" too strong. What is bounded: label **values** come only from CA-issued mTLS common names (D-13), never from caller-supplied text, and `MaxTrackedSinks` caps the registry at 1000 entries with oldest-last-seen eviction, so the server exports at most 1000 per-identity series at any one time. What is **not** bounded: the number of distinct label values a backend has observed over the process's lifetime — an evicted CN that reconnects reappears, and the backend retains both. The mitigation therefore rests on the label source being an issuing-CA decision, not on the eviction ceiling. Separately, the change ID is deliberately reduced to a 0/1 convergence gauge rather than emitted as a label, because a value that changes on every mutation would be unbounded by construction; and the render-failure counter that bypassed the registry entirely has been removed (review M5). |
| T-1-17 | Tampering | a consumer reporting false last-success or failure counts | low | accept | The consumer is the only party that knows whether its local render and write succeeded; the value is inherently self-reported. The independently server-observed `last_seen` and `sinks_connected` signals are not consumer-supplied, so a lying consumer cannot fake liveness. |
| T-1-18 | Information Disclosure | a certificate common name appearing in exported metrics | low | accept | Common names are already the deployment's operator-chosen consumer identifiers and are visible to anyone holding the metrics endpoint, which is an operator-controlled surface.
