# Phase 1 Plan 05 — Sink Health Primitives — Identity, Registry, Gauges

<objective>
Build the three server-side primitives sink health needs, as standalone, unit-tested
units with no RPC wiring: mTLS common-name extraction, an in-memory per-consumer
health registry, and the OTel observable gauges that project it.

Plan 06 wires these into the `WatchHosts` handler. Keeping them separate here means
the concurrency work in plan 06 lands against primitives that are already proven.

Purpose: D-09 puts sink health on the server's existing OTel pipeline instead of
standing up an OTel publisher at every consumer; D-10 keeps last-seen alive across a
closed stream so absence becomes a measurable age; D-13 bounds label cardinality by
verified identity.
Output: `commonNameFromContext`, `SinkHealth`, `(*Metrics).RegisterSinkGauges`.
</objective>

  <behavior>
- Recording that a common name was seen stores a last-seen timestamp for that name.
- Recording a status report stores the reported last-success time and consecutive-failure count for that name.
- After the stream for a name closes, the stored last-seen and last-success values remain readable — closing does not delete the entry.
- The connected-stream count rises on connect and falls on disconnect, and never goes negative even if disconnect is called more times than connect.
- Two goroutines recording concurrently for different names, and a third snapshotting, produce no data race under `-race`.
- Once the tracked-identity ceiling is reached, recording a new name evicts the entry with the oldest last-seen timestamp rather than growing without bound.
- A snapshot returns a copy: mutating the returned map or slice does not affect the registry.
  </behavior>
  <action>
Create `internal/server/sinkmetrics.go`.

Define `type SinkState struct { LastSeen time.Time; LastSuccess time.Time;
ConsecutiveFailures int64; ContractVersion string }` and
`type SinkHealth struct { mu sync.Mutex; states map[string]SinkState;
connected int64 }` with `func NewSinkHealth() *SinkHealth`.

Methods, all taking the common name as the first argument:
`RecordSeen(cn string)` sets `LastSeen` to `time.Now().UTC()`;
`RecordStatus(cn string, lastSuccess time.Time, consecutiveFailures int64, contractVersion string)`
updates those three fields and also refreshes `LastSeen`;
`RecordConnected(cn string)` increments the connected counter and refreshes
`LastSeen`; `RecordDisconnected(cn string)` decrements the connected counter,
clamped at zero, and deliberately leaves the state entry in place — that
retention is D-10 and is what removes the clean-shutdown-versus-crash ambiguity;
`Snapshot() (map[string]SinkState, int64)` returns a defensive copy of the map
plus the connected count.

Declare `MaxTrackedSinks = 1000` with a doc comment explaining that identities
are CA-issued mTLS common names and therefore already bounded, and that this
ceiling is a second, structural guarantee that metric label cardinality cannot
grow without bound (D-13). When a write would insert a name beyond the ceiling,
evict the entry whose `LastSeen` is oldest before inserting, and log the eviction
at warn level with `slog` using structured key-value pairs in the style of
`service.go:130-168`.

All methods must be safe for concurrent use — this registry is written from N
concurrent stream goroutines and read from the OTel scrape callback.

<threat_model>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| mTLS peer certificate to metric label | The only identity permitted to become a metric label value crosses here |
| consumer status report to server state | Values a consumer reports about its own health are stored server-side |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-1-15 | Spoofing | a consumer claiming another consumer's identity to poison its health metrics | high | mitigate | Identity is read only from `VerifiedChains[0][0].Subject.CommonName` on a connection the server already required and verified a CA-signed client certificate for (`internal/server/server.go:207`). No request-body field participates in identity, asserted by an acceptance criterion. |
| T-1-16 | Denial of Service | metric-storage exhaustion via unbounded label cardinality | high | mitigate | Two independent bounds: labels come only from CA-issued common names (D-13), and `MaxTrackedSinks` caps the registry at 1000 identities with oldest-last-seen eviction, so even a compromised CA cannot grow the label set without bound. |
| T-1-17 | Tampering | a consumer reporting false last-success or failure counts | low | accept | The consumer is the only party that knows whether its local render and write succeeded; the value is inherently self-reported. The independently server-observed `last_seen` and `sinks_connected` signals are not consumer-supplied, so a lying consumer cannot fake liveness. |
| T-1-18 | Information Disclosure | a certificate common name appearing in exported metrics | low | accept | Common names are already the deployment's operator-chosen consumer identifiers and are visible to anyone holding the metrics endpoint, which is an operator-controlled surface. No change to the existing metrics trust posture. |
| T-1-SC | Tampering | npm/pip/cargo installs | high | mitigate | Not applicable: `peer` and `credentials` ship inside the pinned `google.golang.org/grpc v1.83.0`; 01-RESEARCH.md's Package Legitimacy Audit records zero new external packages and no install task exists in this plan. |

</threat_model>
