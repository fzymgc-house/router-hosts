# Phase 1 Plan 02 — Template Data Contract — Version Gate and Published Field Set

<objective>
Turn the template data shape proven by the tracer into an explicit, versioned,
published compatibility surface, and make a version mismatch a loud refusal instead
of a silently wrong render.

Purpose: TMPL-02 is the phase's highest-risk requirement. Once consumers depend on a
field set, that set becomes a compatibility obligation the proto contract does not
cover. D-05 converts a future field rename from a silent wrong-render into a startup
error.
Output: contract-version declaration and enforcement in `internal/client/template`,
the contract-v1 sanitizing FuncMap, `docs/reference/template-contract.md`, and three
shipped example templates.

**Revised 2026-07-31 after cross-AI review** (`01-REVIEWS.md` M1, adopted as CONTEXT
D-17). The original plan documented raw `.Comment`/`.Tags` as the template author's
problem and shipped examples that embedded them directly. That reopens the exact
newline/directive-injection class GH #349 closed, at every consumer that copies an
example. This revision publishes a sanitizing function as part of contract v1 and
uses it in every shipped example. pi's argument for deciding now is decisive: adding
FuncMap entries later is a compatible change, but doing it after examples ship means
two generations of consumer templates and no way to recall the ones already in the
wild. This plan also picks up round-1 review L5 (assert the unbound example's rendered
text in full, not just declaration counts) and documents TMPL-08's `.ChangeID`, the
amended TMPL-06 scope, and D-12a's three outcomes.

**Revised 2026-08-01 after cross-AI review round 2** (`01-REVIEWS.md` M1, L5, L8, L9).
Four changes, all in what the documentation promises and how the sanitizer claim is
gated.

**M1 — the contract page must not institutionalize a stronger claim than the mechanism
supports.** Plan 01 now derives the change ID *before* reading the entries (round-2
H1), which makes it a **lower bound** on the state the entries reflect rather than an
exact identity: a mutation landing between the ID read and `ListAll` puts entries in
the snapshot the ID does not yet name. That is safe and self-correcting, but
`.ChangeID` becomes a consumer-visible compatibility surface the moment plan 01 ships,
so the page must say what it actually guarantees. Codex put it directly: `.ChangeID`
cannot truthfully be described as identifying the exact streamed state until an atomic
snapshot read exists, and that read is deferred.

**L8 — "exactly one CR/LF replacer" was an implementation-shape gate, not a behavioral
one.** A repository-wide count of `strings.NewReplacer("\n"` fails the moment anyone
adds unrelated, legitimate sanitization elsewhere in `internal/`, and it passes even if
the two call paths somehow diverge in behavior. The gate is replaced with a scoped
grep over the one file the replacer left, plus a test asserting the server generator
path and the template FuncMap path produce identical output for the same input — which
is the property that actually matters.

**L9 — the version constant moved.** Plan 01 now defines it in `internal/contract`, so
this plan's tests compare against `contract.TemplateVersion` and the client template
package never imports `internal/server`.

**L5 — one honest line about `.Comment`.** `GetComment()` returns `""` for an absent
comment, so a template cannot distinguish nil from empty. No behavior is lost today,
but the page must say so, or a future contract v2 may accidentally promise a
distinction the wire never carried.
</objective>

For `.ChangeID`, state four things and no more, because this field is the phase's
newest compatibility surface and overclaiming it is what review M1 flagged:

- It is the ULID of the newest event in the server's log **as of the moment the
  snapshot began**.
- It identifies **state rather than transmission**, so the same server state yields
  the same value for every consumer — which is what makes "resolver-a and resolver-b

  server reads the ID before it reads the entries, so a mutation landing in between
  puts entries in the snapshot that the ID does not yet name. Convergence is therefore
  **eventual within one notify cycle**: that mutation's own notification delivers a
  further snapshot carrying a strictly greater ID, and the consumer renders again. Say
  plainly what an operator can conclude from a matching change ID — "this consumer has
  rendered at least the state named by this ID" — and what they cannot: "this
  consumer's artifact contains exactly that state and nothing newer". Do **not** write
  that the ID identifies the exact streamed state; an atomic single-transaction
  `{entries, latestEventID}` read would be needed for that and is deferred to a
  follow-up issue tracked alongside #400.
- It is the empty-log zero ULID on a fresh server, a compaction advances it without
  changing host state, and consumers compare it by exact string equality — never by
  prefix, ordering, or numeric comparison.
