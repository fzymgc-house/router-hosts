# Phase 1 Plan 01 — Tracer — End-to-End Consumer-Rendered Output

<objective>
Prove the whole consumer-rendered-output architecture end to end on one thin path: a
caller supplies a `text/template` file, the CLI opens a new `WatchHosts` stream, the
server streams host entries plus a snapshot terminator, and the CLI renders the
template locally and writes the artifact atomically.

This is the phase tracer. Every layer the phase will modify is touched here — proto
contract, server streaming handler, client template package, CLI command, shared
atomic-write helper — with exactly one path wired through. Every later plan expands
outward from this proven slice.

Purpose: D-01 (client-side execution) and D-03 (struct top-level value) are one-way
decisions. Proving them end to end on the first commit means an architectural
dead-end costs one plan, not ten.
Output: `WatchHosts` RPC, `internal/contract`, `internal/server/watch.go`,
`internal/client/template`, `router-hosts render` command, and `internal/atomicfile`.

**Revised 2026-07-31 after cross-AI review round 1** (`01-REVIEWS.md`). This plan
absorbs TMPL-08 (change identity, CONTEXT D-18 to D-22) into the tracer, because the
change ID is a metadata field of the D-03 contract struct and the tracer is what proves
that contract end to end. It also picks up review findings L3, L4, L7 (proto contract
comments) and L8 (bound the render drain loop instead of waiting for plan 03).

**Revised 2026-08-01 after cross-AI review round 2** (`01-REVIEWS.md`, H1/H2/L1/L7/L9).
Four changes:

**H1 — the derivation order was backwards, and both reviewers found it independently
from opposite directions.** The round-1 plan said to derive the change ID *after*
reading the entries "so the ID can never claim to describe state newer than what was
actually sent". It guarantees the opposite. A mutation committing between `ListAll` and
`LatestEventID` produces a terminator holding entries(S1) labelled with ID2. The
consumer renders S1 and records ID2; the mutation's own notify then delivers
entries(S2) also labelled ID2, plan 07's D-21 client skip fires on the matching ID, and
the consumer serves S1 forever while reporting itself converged. No later snapshot ever
changes the ID unless another mutation lands. This is exactly the failure TMPL-08 was
added to prevent, reintroduced through the terminator instead of through ULID
generation — and every test the round-1 plan specified passes with the wrong order, so
it would have shipped silently. **The derivation is now strictly before `ListAll`**, in
this plan and in plan 06's shared `sendSnapshot`, and the accompanying comment is
inverted. Deriving first makes the ID a *lower* bound: a snapshot may carry entries
newer than its ID, the follow-up snapshot then carries a strictly greater ID, and the
consumer re-renders. The cost is one redundant render; the alternative is a permanent
stale zone.

**Atomicity is deliberately deferred, not overlooked.** Codex's stronger remedy — a
single SQLite read transaction returning `{entries, latestEventID}`, or read-ID →
read-entries → read-ID-again with retry — would make the ID name the entries exactly.
It needs a new transaction-scoped `storage.HostProjection` method, which is a
storage-layer change of the same class as the `ListAll` laziness already deferred to
**#400**, and REVIEWS.md itself recommends deferring it. The flip removes the hazard;
atomicity would only let the contract doc keep stronger wording. **Action for the
executor: file the atomic-snapshot read as a follow-up issue alongside #400 and record
its number in this plan's SUMMARY.** Plan 02's contract page states `.ChangeID` as a
lower bound with convergence eventual within one notify cycle (review M1), which is the
honest description of what ships.

**H2 — the storage half moved out.** The round-1 plan had this task add
`EventStore.LatestEventID`, its sqlite implementation and its compliance case, and
write a doc comment warning that "any future change to ID generation must preserve
monotonicity". Codex found the counterexample already in the repo:
`internal/storage/sqlite/eventstore.go:258` mints the compaction seed with a bare
`ulid.Make()`, so `MAX(event_id)` can fail to advance or regress today. That is a
prerequisite, not a caution, so the whole storage-layer foundation — the shared
monotonic generator plus `LatestEventID` — is now **plan 01-09 in wave 1**, and this
tracer consumes it. This plan no longer touches `internal/storage`.

**L9, L7, L1 — three smaller corrections.** The contract-version constant moves to a
neutral `internal/contract` package so client-template tests do not import
`internal/server` (L9); the `int32` entry count is validated before conversion rather
than allowed to wrap (L7); and the render drain bound is a package-level `var` rather
than a `const`, because the round-1 plan declared a `const` and then specified a test
that "temporarily lowers" it, which does not compile (L1).
</objective>

**TMPL-06 scope, per the amended requirement (`.planning/REQUIREMENTS.md` TMPL-06,
amended 2026-07-31 after `01-REVIEWS.md` H2):** the requirement now reads *bounded
wire messages with client backpressure*, and explicitly defers storage-layer
laziness. This phase delivers exactly that: one `HostEntry` per `stream.Send` on
`WatchHosts`, plus chunked sends on `ExportHosts`, which bounds per-message wire
memory and gives the client gRPC flow-control backpressure. It does **not** make
`store.ListAll()` a cursor read — that needs a new cursor-based
`storage.HostProjection` method and is tracked in **#400**. No plan in this phase
claims O(1) server memory; roadmap success criterion 5 was rescoped to match.

3. `internal/server/watch.go` (new) — implement
`func (s *HostsServiceImpl) WatchHosts(stream grpc.BidiStreamingServer[hostsv1.WatchHostsRequest, hostsv1.WatchHostsResponse]) error`.
Call `stream.Recv()` once to read the opening request; treat `io.EOF` on that
first Recv as a client that hung up and return nil. If the request's `GetFollow()`
is true, return `status.Error(codes.Unimplemented, "follow mode is not implemented yet")`
— plan 06 replaces this branch with the concurrent goroutine pair.

Otherwise, in this exact order:

   a. Call `s.store.LatestEventID(stream.Context())` and hold the result. Convert a
   storage error through the existing `mapError`. Set the wire value to the ULID's
   string form, or to `storage.ZeroChangeID` when the log is empty.
   b. Call `s.store.ListAll(stream.Context())`, converting a storage error through
   `mapError`.
   c. Send one `WatchHostsResponse` per entry carrying `domainToProto(&entries[i])`
   in the `entry` oneof arm — mirror `ListHosts` at `service.go:319-333`, returning
   the raw send error unwrapped.
   d. Guard the count before converting: if `len(entries)` exceeds `math.MaxInt32`,
   return `status.Error(codes.Internal, ...)` naming the count, rather than letting
   `int32(len(entries))` wrap to a negative value (review L7). The client's
   configured 50,000-entry ceiling does not constrain the server's inventory, so this
   guard is the server's own.
   e. Send one final `WatchHostsResponse` carrying `SnapshotComplete` with `Count`
   set to the validated `int32`, `GeneratedAt` set to
   `timestamppb.New(time.Now().UTC())`, `ContractVersion` set to
   `TemplateContractVersion`, and `ChangeId` set to the value captured in step (a).
   Return nil.

**Step (a) runs BEFORE step (b). This ordering is the H1 fix and it is load-bearing.**
Write a comment at the derivation site saying so, in these terms and in this
direction. Reading the ID first makes it a **lower bound** on the snapshot: a mutation
landing between the read and `ListAll` puts entries in the snapshot that the ID does
not yet name, and the ID is then corrected by the next snapshot, which carries a
strictly greater ID and therefore does not match what the consumer recorded — costing
one redundant render. Reading the ID **last** produces the opposite and unrecoverable
error: the snapshot would carry entries from before the mutation labelled with the ID
from after it, the consumer would record that newer ID against older entries, and the
mutation's own follow-up snapshot would carry the same ID and be skipped by the D-21
client-side dedupe in plan 07 — leaving the consumer serving a stale zone permanently
while reporting itself converged. No later snapshot changes the ID unless another
mutation happens to land. Say plainly in the comment that swapping these two calls
reintroduces that bug and that no test in the suite catches it by timing alone.

Note in the same comment what this ordering does **not** buy: the ID still does not
name the entry set exactly, because reads are not held under the write queue (which is
scoped to mutations, `service.go:784`). Making it exact needs a single-transaction
`{entries, latestEventID}` read, which is deliberately deferred — see this plan's
objective and the follow-up issue filed alongside #400. Do not describe the ID as
identifying the exact streamed state.
