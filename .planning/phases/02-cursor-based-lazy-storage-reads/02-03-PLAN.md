<objective>
Pin LAZY-03 and write the read-path contracts down where an operator will find them.

D-06 established that a page fetch loads and replays one aggregate atomically, so LAZY-03's
literal scenario — a cursor sitting inside an aggregate's pre-compaction history while that
aggregate is compacted — cannot occur. RESEARCH.md confirmed the mechanism by reading
`CompactAggregate`: it deletes the aggregate's event rows and inserts one `HostCompacted`
seed for the SAME `aggregate_id` with a freshly minted `event_id`, so the aggregate's keyset
position never changes and any page fetch sees one atomic replay result.

LAZY-03 is satisfied by documenting that impossibility and pinning the two reachable
variants with tests. That reading is recorded as a flagged assumption in this plan's
frontmatter, because the edge probe returned `unclassified` for LAZY-03 and it is not this
plan's place to auto-resolve it.

Purpose: without this plan LAZY-03 would ship as a doc comment nobody executed, and D-09's
and D-10's contracts would live only in a CONTEXT.md that no operator reads.

Output: two conformance tests and an operator-facing architecture section.
</objective>

    State, concretely:

    D-10: reads iterate aggregates in strictly ascending aggregate-ULID order. This is now an
    explicit `ORDER BY aggregate_id`, is a documented contract rather than an accident of the
    query planner's covering-index scan, and is pinned by tests. Note that it was verified
    against the real driver to reproduce the previous de-facto order exactly, so no rendered
    output changed when it landed.

    D-09: a paged read gives snapshot-per-page, not snapshot-for-the-whole-read. Spell out the
    three parts precisely:
    - Every aggregate present when the read started is yielded exactly once. Aggregate IDs are
      immutable, so none is skipped or duplicated. Set membership is the strong guarantee.
    - An aggregate created mid-read sorts ahead of the cursor and is normally included.
      Attribute this to the strictly monotonic `internal/eventid` singleton that
      `CommandHandler.newID` mints through — NOT to `ulid.Make()`. Within this single-process,
      single-`WriteQueue` deployment there is no same-millisecond ordering ambiguity for newly
      created aggregates.
    - An entry's VALUE reflects the instant its page was fetched, not one global instant. This
      is the real weakness and it must be stated as such, not softened.

    Explain WHY, in one short paragraph: `withConn` takes a connection from a 10-connection
    `sqlitex.Pool` and returns it per call, so consecutive pages run on different connections.
    Add that this follows from the per-call checkout regardless of journal mode, that the pool
    is NOT in WAL mode today (no `PrepareConn` hook and no `journal_mode` pragma anywhere in
    `internal/storage/sqlite`), and that enabling WAL would be a prerequisite for a true
    cross-page snapshot but not sufficient on its own — a single pinned connection held across
    pages would also be required, which the current shape deliberately does not do.
