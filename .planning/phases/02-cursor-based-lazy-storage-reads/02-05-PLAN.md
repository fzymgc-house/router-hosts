<objective>
Make the memory claim honest, then measure it.

D-01 is the most load-bearing output of this phase's discussion: LAZY-02 and ROADMAP SC2
assert that peak memory "no longer scales with total event-log size", and that was ALREADY
TRUE before this phase began. `ListAll` loops aggregate-by-aggregate, reassigning its events
slice each iteration, and `replayEvents` returns a single `*domain.HostEntry` retaining no
reference to that slice. No benchmark can show that improving. The claim is amended to total
ENTRY COUNT, which is what the cursor genuinely bounds — routed through a human sign-off,
following TMPL-06's 2026-07-31 precedent exactly.

Then the benchmark. D-11 asserts a ratio across two fixtures rather than an absolute ceiling,
and RESEARCH.md's Pitfall 1 is the reason the metric choice is not a detail: `AllocsPerRun`
and `-benchmem` report cumulative allocation, which is O(N) for the paged and drained paths
alike. Only a peak sampled DURING the call distinguishes them. LAZY-02's own requirement text
says "(`AllocsPerRun`/memstats)"; this plan resolves that tension explicitly by making
memstats peak-sampling the primary metric and reporting the cumulative figures as secondary,
informational output.

Purpose: a benchmark that measures the wrong quantity would either "disprove" a real win or
green a claim nobody verified. Both are worse than no benchmark.

Output: an amended requirement, a shared peak-heap sampler, and two build-tagged benchmarks.
</objective>
